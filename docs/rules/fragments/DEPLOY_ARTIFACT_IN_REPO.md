## DEPLOY_ARTIFACT_IN_REPO

**A built deployment archive (`.mtar`) lies in the project and no `.gitignore` pattern excludes it.** The Cloud MTA Build Tool writes the archive to `mta_archives/` next to the sources by default, and the archive holds everything the deployer needs: the resolved `node_modules` of every module, built front-end bundles, the deployment descriptor and every configuration file that was in scope when `mbt build` ran, including `default-env.json`-style files and `.mtaext` extension descriptors that were not excluded. Without an ignore pattern the next `git add .` commits it, and a repository history keeps it even after the file is deleted. Committed archives also tempt a deployment from the repository instead of from a reproducible build, so the artifact that reaches production is one nobody can trace back to a pipeline run.

- **Data:** every `*.mtar` outside the skipped directories (`node_modules`, `.git`, `gen`, `dist`, `dist-report`, `target`, `build`, `coverage`, dot-directories), recorded as `archives[]` with the relative file name, its size from `lstat` and whether a `.gitignore` pattern matches it; the archive itself is never opened. `repository` is whether `<root>/.git` exists (`lstat` only; a `.git` file of a worktree counts too), and `gitIgnore.present` whether a root `.gitignore` exists. Matching uses the root `.gitignore` and the `.gitignore` files in the directories along the archive's path (comments, blank lines, `!` negation, leading `/` anchoring, trailing `/`, `*`, `?`, `**`, character classes, patterns without a `/` at any depth, last match wins).
- **Trigger:** an archive with `ignored === false`. One finding per archive file per project; the subject is the relative file name.
- **Severity:** from the criticality matrix, both inputs recorded in the evidence.
  - `medium` (impact `moderate`, ease of attack `advanced`) when `repository` is true: a `.git` directory is present, so the archive is one `git add .` away from the history, or already in it.
  - `low` (impact `minor`, ease of attack `complex`) when `repository` is false: nothing tracks the folder yet, so the archive only lingers on disk until the project is put under version control or packed up and shared, an extra step before anyone else can get at it. (The design table wrote this cell as `minor` × `advanced`, which the matrix maps to `medium`; `complex` is the pair that yields the intended `low`.)
- **Evidence:** `subject` (archive file), `bytes` (size), `ignored` (always `false`), `repository`, `tracked` (always `'unknown'`: the scan runs no `git` command, so whether the file is already committed is not known), `impact`, `easeOfAttack`.
- **Location:** the archive file; no line.
- **Remediation:** Add `*.mtar` (or the build output folder, usually `mta_archives/`) to the root `.gitignore`. If the archive was already committed, stop tracking it with `git rm --cached <file>` and commit; if it reached a shared remote, treat every credential in its configuration files as exposed and rotate it, since removing the file does not remove it from the history. Build the archive in the pipeline with `mbt build` and deploy from there instead of keeping it next to the sources.
- **References:** <https://git-scm.com/docs/gitignore>, <https://sap.github.io/cloud-mta-build-tool/usage/>, <https://help.sap.com/docs/btp/sap-business-technology-platform/multitarget-applications-in-the-cloud-foundry-environment>, <https://owasp.org/Top10/2025/A03_2025-Software_Supply_Chain_Failures/>
- **Limits / what does not trigger:**
  - An archive that a `.gitignore` pattern matches produces nothing, whether or not the folder is a repository. The rule checks the ignore configuration, not the index: an archive that was committed before the pattern was added is still in the history and is still reported as ignored, hence `tracked: 'unknown'`. Running `git ls-files '*.mtar'` answers that question.
  - Only `.gitignore` files are read: `.git/info/exclude`, the global `core.excludesFile` and the ignore rules of other version control systems are not, so an archive excluded only there is reported. Conversely, the matcher treats a file inside an ignored directory as ignored even when a deeper pattern re-includes it, which matches git ("It is not possible to re-include a file if a parent directory of that file is excluded").
  - A root `.gitignore` that exists but does not cover the archive still triggers; the `gitIgnore.present` flag changes nothing. The pattern must come from the project itself: the repository that ships `btp-lens` ignores `*.mtar`, but that does not help a scanned project.
  - Archives under skipped directories (for example `dist/` or `target/`) are never seen, and the walk stops after 20 000 entries or 200 archives. Other packaged artifacts (`.zip`, `.jar`, `.war`, `.tgz`) are out of scope: the rule is about the MTA archive, the artifact `mbt build` writes into the project by default.
  - `repository` is the presence of `<root>/.git` only. A project scanned from a subdirectory of a repository, or whose `.git` lives elsewhere (`--git-dir`, `GIT_DIR`), is reported as `repository: false` and therefore `low`; a `.git` directory left by a template clone is reported as `true`.
  - The `gitignore(5)` manual was verified through the `git/git` GitHub mirror (`Documentation/gitignore.adoc`: "Files already tracked by Git are not affected; see the NOTES below for details", "To stop tracking a file that is currently tracked, use `git rm --cached` to remove the file from the index"); the link is the canonical page it publishes to. The Cloud MTA Build Tool usage page was verified through the `SAP/cloud-mta-build-tool` mirror (`docs/docs/usage.md`: "If this parameter is not provided, the `MTAR` file is saved in the `mta_archives` subfolder of the current folder", default name `<mta_application_ID>_<mta_application_version>.mtar`); `sap.github.io` does not resolve from the build environment, so the link is the canonical published page. The SAP Help page was verified through the `SAP-docs/btp-cloud-platform` mirror (`docs/30-development/multitarget-applications-in-the-cloud-foundry-environment-d04fc0e.md`, which defines the archive as "Archive containing a deployment descriptor, the module and resource binaries, and configuration files"); `help.sap.com` does not resolve either, so the link is the canonical page that file publishes to.
