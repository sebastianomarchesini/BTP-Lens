## CAP_PERSONAL_DATA_UNANNOTATED

**Entity holds personal data without @PersonalData annotations.** An entity has elements that look like personal data (names, contact details, identifiers such as a tax id or an IBAN, or address parts on an entity that belongs to a person), but neither the entity nor an `annotate` statement carries `@PersonalData`. CAP derives its data-privacy handling from these annotations: the `@cap-js/audit-logging` plugin logs reads of sensitive and changes of personal data only for annotated entities, and the data-retention and personal-data-manager integrations find data subjects through them. Without the annotations the data is stored and served like any other, so access to it is neither logged nor governed.

- **Data:** the CDS facts the project collector keeps per `*.cds` file: top-level and namespaced entity names, their element names, their associations and compositions (`{ field, target }`), `using … as` aliases, whether `@PersonalData` appears on the entity header or any element, and `annotate` statements with whether `@PersonalData` appears anywhere in them. No element types, values, titles or other annotations are read. The rule reads them through the shared model helper `personalEntities`, which resolves aliases and namespace-qualified names and merges `annotate` statements (an annotate on a service projection counts for the db entity when that projection is `as projection on` it).
- **Trigger:** an entity that is personal by one of three reasons, and not `@PersonalData` after merging annotates. One finding per entity; the subject is the entity name as written.
  - `strong-fields`: at least one element whose name (lowercased, `_`/`-` removed) is in the strong list of `analyzers/project/patterns.ts` (`email`, `phone`, `mobile`, `firstName`, `lastName`, `birthDate`, `ssn`, `taxId`, `iban`, `creditCard*`, `salary`, `gender`, `religion`, …, and `*phone`/`*mail`/`*fax`/`*email` suffixes such as `workEmail`).
  - `linked-entity`: only weak elements (`street*`, `city`, `postCode`, `zipCode`, `latitude`, `longitude`, `country`) and an association or composition to an entity that has a strong element or is `@PersonalData`.
  - `entity-name`: only weak elements and the entity's last name segment matches `address|contact|person|customer|employee|user|patient|member|applicant` (case-insensitive).
- **Severity:** `medium` = (`moderate`, `advanced`) for every branch: an attacker needs an account or a foothold to reach the data, and what the missing annotation costs is the logging, retention and subject-request handling CAP would apply, not the data itself. The three titles name the reason: "Entity holds personal data without @PersonalData annotations", "Entity holds address data of a personal entity without @PersonalData annotations", "Entity whose name suggests personal data holds address data without @PersonalData annotations" (the name pattern also matches `Addresses`, `Contacts` and `UserSettings`, which are not persons, so the title does not say so).
- **Evidence:** `subject` (entity name), `reason` (`strong-fields`, `linked-entity` or `entity-name`), `strongFields` and `weakFields` (the matching element names, in model order), `linkedTo` (the personal entity an association points to when that is the reason, else `null`), `impact`, `easeOfAttack`. Only identifiers are copied: no element types, defaults, titles or doc comments.
- **Location:** the `.cds` file and the line of the `entity` definition.
- **Remediation:** Annotate the entity, preferably in a separate `db/data-privacy.cds` file: `annotate <Entity> with @PersonalData: { EntitySemantics: 'DataSubject', DataSubjectRole: '<Role>' }` for the entity that represents the person, or `EntitySemantics: 'DataSubjectDetails'` for an entity that belongs to one through an association; mark the key, or the association to the data subject, with `@PersonalData.FieldSemantics: 'DataSubjectID'`, each personal element with `@PersonalData.IsPotentiallyPersonal` and sensitive ones (salary, religion, card numbers) with `@PersonalData.IsPotentiallySensitive`. With the `@cap-js/audit-logging` plugin in place (`cds add audit-logging`; `CAP_AUDITLOG_MISSING` reports when it is not), changes of personal and reads of sensitive elements are then logged. The finding is inferred from element and entity names: if the elements are not personal data (a warehouse address, a company's contact mailbox), rename them so they no longer look like it, or accept the finding.
- **References:** <https://cap.cloud.sap/docs/guides/security/dpp-annotations>, <https://cap.cloud.sap/docs/guides/security/dpp-audit-logging>, <https://owasp.org/Top10/2025/A04_2025-Cryptographic_Failures/>, <https://owasp.org/Top10/2025/A09_2025-Security_Logging_and_Alerting_Failures/>
- **Limits / what does not trigger:**
  - Entities with weak elements only that neither link to a personal entity nor are named like one (`Warehouses` with `city` and `postCode`, `Plants` with coordinates) produce no finding, nor do entities without any personal-looking element (`Incidents` with `title` and `status`), even when they link to a customer. An association to an entity that is itself not personal does not count.
  - `@PersonalData` declared inline on the entity or one of its elements, through an `annotate` on the entity (by exact name, `using` alias or namespace-qualified suffix), or through an `annotate` on a service projection whose `as projection on` resolves to the entity, suppresses the finding. An annotate on a service entity that is not a recognisable projection (no `projectionOf`) does not reach the db entity, so the finding stays. The rule checks only that `@PersonalData` is present somewhere on the entity, not that `EntitySemantics`, `DataSubjectID` or the element-level flags are complete, and it does not check whether the audit-logging plugin is installed (`CAP_AUDITLOG_MISSING` does).
  - The inference uses the English field-name lists in `analyzers/project/patterns.ts`: a personal entity whose elements are named differently (`col1`, abbreviations, non-English names) is not recognised, and a non-personal element that happens to match (`country` of a plant, `mail` as a postal batch) may be reported; the `entity-name` branch matches on the name alone, so a non-personal entity such as `UserSettings` or `Regions` that is named like one and has an address element is reported too. An association from a weak-field entity counts only when its target has a strong element or `@PersonalData`: a target that is personal by its name alone (`Contacts` with `city` only) does not make the linking entity personal, and a self-association never does. Entities defined inside a service block (`service S { entity X { … } }`) are collected as service entities, not db entities, and are not checked here.
  - Two files that define an entity with the same written name (for example the same `entity Customers` under two namespaces) yield one finding, located at the first file in path order; the collector stores names as written, so the rule cannot tell them apart.
  - The CAP documentation pages were verified from the `cap-js/docs` GitHub mirror (`guides/security/dpp-annotations.md`, which documents `EntitySemantics` with the values `DataSubject`, `DataSubjectDetails` and `Other`, `DataSubjectRole`, `FieldSemantics: 'DataSubjectID'`, `IsPotentiallyPersonal`, `IsPotentiallySensitive` and the separate `data-privacy.cds` file; and `guides/security/dpp-audit-logging.md`, which documents the `PersonalDataModified` and `SensitiveDataRead` events the plugin emits) because `cap.cloud.sap` does not resolve from the build environment; the links are the canonical pages those files publish to. The OWASP links follow the `A04_2025-Cryptographic_Failures` and `A09_2025-Security_Logging_and_Alerting_Failures` entries in the OWASP/Top10 `2025/mkdocs.yml`.
