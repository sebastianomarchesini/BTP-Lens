## CAP_MOCKED_AUTH_IN_PROD

**A development authentication strategy is configured for production.** The effective CAP configuration for the `production` profile selects `mocked`, `dummy` or `basic` authentication. With `mocked`, the pre-defined mock users shipped with `@sap/cds` (`alice`, `carol`, `dave` and `erin` carry the `admin` role) are merged into the project's `users`, and the default `"*": true` entry accepts any other login as well, unless the project overrides them; with `basic`, the users listed in the project files are accepted (the pre-defined ones are off). `dummy` accepts every request and switches `@requires` and `@restrict` off, and `mocked` in production also switches off the implicit `@requires: 'authenticated-user'` on unannotated services. CAP itself defaults to `jwt` in production, so this only happens when the project sets it.

- **Data:** `cds.effective.production.authKind`, computed by the project collector from `.cdsrc.yaml`, `.cdsrc.json` and `package.json#cds` merged in cds order, with `[production]` and `[production!]` blocks applied at every nesting level; `requires.auth` as a string or `requires.auth.kind`. `sourcesRead` records which of the three files existed.
- **Trigger:** `authKind` is `mocked`, `dummy` or `basic`. One finding per project; the subject is the configuration key `requires.auth`.
- **Severity:** `critical`, from the criticality matrix with impact `severe` (full impersonation of any user, or no authentication at all) and ease of attack `easy` (a public user name such as `alice`, a name and password committed to the repository, or nothing at all is enough). Both inputs are recorded in the evidence.
- **Evidence:** `subject` (`requires.auth`), `authKind`, `sourcesRead` (in cds priority order, lowest first), `sourcesNotRead` (the fixed list `.cdsrc-private.json`, `.cdsrc.js`, `.env`, `CDS_* environment variables`), `impact`, `easeOfAttack`.
- **Location:** the source read that cds applies last (`package.json`, else `.cdsrc.json`, else `.cdsrc.yaml`), without a line. No location when none of the three files existed.
- **Remediation:** Configure a production authentication strategy, for example in `package.json`: `"cds": { "requires": { "[production]": { "auth": "xsuaa" } } }` (or `"ias"`), bind the app to an XSUAA or IAS instance, and keep `mocked` and its users under `[development]` only. Verify the result with `cds env get requires.auth --profile production`.
- **References:** <https://cap.cloud.sap/docs/node.js/authentication>, <https://cap.cloud.sap/docs/node.js/cds-env>, <https://owasp.org/Top10/2025/A07_2025-Authentication_Failures/>
- **Limits / what does not trigger:**
  - `authKind` null (nothing configured) produces no finding: CAP defaults to `jwt` in production. `jwt`, `xsuaa`, `ias`, `ams` and unknown strategies (`other`) produce no finding either.
  - A `mocked` configuration that applies only to the `development` profile does not trigger; mocked users and their passwords are the subject of `CAP_MOCKED_USER_PASSWORD`, and `restrict_all_services` on its own is not a finding.
  - cds reads more sources than the collector opens, because they hold credentials: `.cdsrc.js` (same tier as `.cdsrc.yaml`/`.cdsrc.json`, below `package.json#cds`), and above `package.json#cds` the files `.cdsrc-private.json`, `default-env.json` (deprecated), `.env`, `.<profile>.env` (for example `.production.env`) and the `CDS_CONFIG` and `CDS_*` environment variables. Any of them can still override the strategy at runtime, in either direction, so the finding reflects the committed configuration only and names the main ones in `sourcesNotRead`.
  - The older spellings `mocked-auth`, `basic-auth` and `dummy-auth` are normalised to the current names by the collector and trigger as well.
  - The location names the highest-priority file that existed, not necessarily the one that sets `requires.auth`; the collector does not record which source won the merge.
  - The CAP documentation pages were verified from the `cap-js/docs` GitHub mirror (`node.js/authentication.md`, `node.js/cds-env.md`) because `cap.cloud.sap` does not resolve from the build environment; the links are the canonical pages those files publish to. That page documents `basic` only as the `mocked` strategy without the predefined mock users (the project's own `users` still apply), which is why the rule treats it the same way. The source tiers above are the "Sources for cds.env" table of `cds-env.md`, which also documents `--profile` as a bootstrap argument of the cds CLI (used by the remediation's `cds env get … --profile production`). The OWASP link follows the `A07_2025-Authentication_Failures` entry in the OWASP/Top10 `2025/mkdocs.yml`.
