## XSUAA_SCOPE_UNUSED

**A scope in the XSUAA security descriptor can never be assigned.** No role template references it and it is not granted to another application, so no role, and therefore no role collection and no user, can ever carry it. Such a scope is dead configuration: it suggests a permission that does not exist, or it is the trace of a role template that was removed or renamed without the matching scope, and either way it misstates the authorization model that reviewers and auditors read from the descriptor.

- **Data:** every XSUAA descriptor of the project (`xsSecurity`): each `xs-security.json` found by the walk, and the inline `parameters.config` of every `mta.yaml` resource with `service: xsuaa`; from each, the scope names with whether `granted-apps` or `grant-as-authority-to-apps` is set, and the `scope-references` of every role template. Descriptions, `authorities`, `foreign-scope-references`, `oauth2-configuration` and `xsappname` are never read.
- **Trigger:** a scope without `granted-apps`/`grant-as-authority-to-apps` whose name is not in the `scope-references` of any role template in any descriptor of the project. Names are compared exactly and with a leading `$XSAPPNAME.` stripped from both sides, so `$XSAPPNAME.admin` is satisfied by a reference to `$XSAPPNAME.admin` or to `admin`. One finding per scope name per project (the first descriptor in file order when a name appears twice); the subject is the scope name as written.
- **Severity:** from the criticality matrix, both inputs recorded in the evidence.
  - `low` (impact `minor`, ease of attack `complex`), always: nobody gains access through an unassignable scope; the harm is a misleading authorization model and configuration drift, which only pays off for an attacker combined with other mistakes.
- **Evidence:** `subject` (scope name), `source` (`xs-security.json` or `mta.yaml`), `roleTemplates` (count in the descriptor that defines the scope), `descriptors` (count of descriptors in the project), `impact`, `easeOfAttack`.
- **Location:** the descriptor file (`xs-security.json` or `mta.yaml`); no line, since the collector keeps names only.
- **Remediation:** Reference the scope from a role template in xs-security.json, for example `"role-templates": [{ "name": "Admin", "scope-references": ["$XSAPPNAME.admin"] }]`, so it can be assigned through a role collection, or remove the scope. If another application is meant to call with it, grant it explicitly with `granted-apps` or `grant-as-authority-to-apps`. In a CAP project, regenerate the descriptor with `cds compile srv --to xsuaa` so scopes and role templates stay in step with the roles used in the CDS model.
- **References:** <https://help.sap.com/docs/btp/sap-business-technology-platform/building-roles-and-role-collections-for-applications>, <https://cap.cloud.sap/docs/guides/security/cap-users>, <https://owasp.org/Top10/2025/A02_2025-Security_Misconfiguration/>
- **Limits / what does not trigger:**
  - A scope listed in `granted-apps` or `grant-as-authority-to-apps` is meant for another application and produces no finding, whatever the role templates say. The rule does not check that the named applications exist.
  - A reference in any descriptor of the project counts, not only the one that defines the scope: XSUAA merges the inline `config` of the mta.yaml resource with `xs-security.json` at deployment (CAP, "Publish Security Descriptor": "Inline configuration in the mta.yaml `config` block and the xs-security.json file are merged"). The design table said "in the same descriptor"; the project-wide check was chosen to avoid reporting a scope that a template in the other half of the merged descriptor references. The flip side: in a repository with several unrelated `xs-security.json` files, a template in one application silences a same-named scope in another.
  - Projects without any descriptor, descriptors without scopes, and references to foreign scopes such as `uaa.user` produce nothing: the rule looks only at scopes the project defines. Whether the CDS model uses roles that have no scope is the subject of `CAP_ROLE_NOT_IN_XSUAA`.
  - Only `scope-references` of role templates count as usage. A scope checked in code (`req.user.is('admin')`, `checkScope` in an approuter or XSSEC handler) without a role template is still reported, because it still cannot be assigned to anyone; the finding then asks for the role template, not for code changes.
  - Scope and reference names that are not identifier-shaped (for example `$XSAPPNAME(application,other-app).read` with parentheses) are dropped by the collector and neither reported nor matched. A `*.mtaext` extension descriptor and `xs-security.json` files under skipped directories (`node_modules`, `gen`, `dist`, dot-directories) are never read, so scopes or templates added only there are not seen.
