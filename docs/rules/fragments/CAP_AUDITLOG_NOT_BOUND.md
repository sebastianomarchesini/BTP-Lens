## CAP_AUDITLOG_NOT_BOUND

**Audit logging is installed but no audit log service is bound.** The project depends on the `@cap-js/audit-logging` plugin and its production kind writes to a service binding (`audit-log-to-restv2` finds the SAP Audit Log service by the VCAP label `auditlog`, `audit-log-to-alsng` by the binding name `auditlog-ng`), but the MTA descriptor declares no such instance. This is the state a Node.js project is in right after `cds add audit-logging`, which adds the dependency and the `auditlog` resource but no `cds.requires.audit-log` entry, when the resource is later removed or the descriptor was written by hand. Without a binding the plugin's production service throws `No or malformed credentials for "audit-log"` on the first `cds.connect.to('audit-log')`, which its read and modification handlers await without catching, so the first access to personal data in production fails or, where the error is swallowed higher up, leaves no audit entry, even though the project looks as if it logs them.

- **Data:** `packageJson.dependencies` and `devDependencies` (package names only), `cds.effective.production.auditLogKind` and `auditLogConfigured` (computed by the project collector from `.cdsrc.yaml`, `.cdsrc.json` and `package.json#cds` merged in cds order with `[production]` and `[production!]` blocks applied), and the facts the collector keeps from `mta.yaml` / `mta.yml`: resource `name`, `type`, `parameters.service`, and the `requires` names of every module. No other part of the descriptor is read.
- **Trigger:** `@cap-js/audit-logging` is a dependency, **and** an MTA descriptor exists, **and** the production `audit-log` kind is `audit-log-to-restv2`, `audit-log-to-alsng` or unset (the plugin's own defaults then select `audit-log-to-restv2` for production), **and** the descriptor binds no audit log instance: no resource has `service: auditlog`, no resource of type `org.cloudfoundry.existing-service` or `org.cloudfoundry.user-provided-service` has a name containing `audit`, and no module requires a resource named `auditlog-ng`. One finding per project; the subject is the CF service name `auditlog`.
- **Severity:** `medium` = (`moderate`, `advanced`) from the criticality matrix: an attacker still needs an account or a foothold to touch personal data (`advanced`), and what the missing binding costs is the ability to detect and reconstruct that access afterwards, which `CAP_AUDITLOG_MISSING` rates the same for a project that never set audit logging up (`moderate`). The project here chose audit logging, so the fix is a descriptor change, not a design change.
- **Evidence:** `subject` (`auditlog`), `auditLogKind` (the production kind, or `null`), `auditLogConfigured` (boolean), `modules` and `resources` (counts of entries in the descriptor), `impact`, `easeOfAttack`. Resource, module and service names from the descriptor are not repeated.
- **Location:** `mta.yaml` or `mta.yml` (whichever exists), without a line: the collector keeps no positions from the descriptor.
- **Remediation:** Add an SAP Audit Log service instance to the MTA descriptor and require it from the server module: a resource of type `org.cloudfoundry.managed-service` with `service: auditlog` and `service-plan: premium` (what `cds add audit-logging` generates), or `org.cloudfoundry.existing-service` named after an instance created with `cf create-service auditlog premium <name>`; then list the resource under the module `requires`. The plugin finds the `audit-log-to-restv2` binding by its VCAP label `auditlog`; with Audit Log Service NG (`audit-log-to-alsng`) the binding must be named `auditlog-ng`. Without a binding the audit log service cannot initialise in production and audit entries are not written. Verify with `cds env requires.audit-log --profile production` and `cf services`.
- **References:** <https://cap.cloud.sap/docs/guides/security/dpp-audit-logging>, <https://github.com/cap-js/audit-logging>, <https://help.sap.com/docs/btp/sap-business-technology-platform/audit-log-write-api-for-customers>, <https://owasp.org/Top10/2025/A09_2025-Security_Logging_and_Alerting_Failures/>
- **Limits / what does not trigger:**
  - Projects without `@cap-js/audit-logging` in `dependencies` or `devDependencies` produce no finding, whatever the descriptor says: a project that uses the legacy `@sap/audit-logging` library, or none at all, is `CAP_AUDITLOG_MISSING`'s business. A plugin listed only in `devDependencies` still counts here (it is loadable locally), although it will be missing from the production deployment, which this rule does not detect.
  - Projects without `mta.yaml` / `mta.yml` produce no finding: `manifest.yml`, Kyma/Helm charts and `cf bind-service` done by hand are not read, so a binding created that way is invisible and the rule cannot say anything about it. For the same reason a descriptor that binds an existing instance under a name without `audit` in it (`org.cloudfoundry.existing-service` named `my-logs`) is reported as unbound: the descriptor does not carry the instance's service name, so the resource name is the only clue, and the finding then asks for a recognisable name or a `service: auditlog` managed resource.
  - A production kind of `audit-log-to-console`, `audit-log-to-library` or any other string (`audit-log-to-als`, a custom kind) produces no finding: those kinds need no binding, or the rule cannot tell what they need. A configuration without a `kind` (`audit-log: true`, or an object that only sets `impl`, `handle` or `outbox`) keeps the plugin's production default and fires; a custom `impl` that needs no binding is therefore reported, since the collector keeps no `impl` fact. `audit-log: false` in production, which disables the service, is indistinguishable from an absent configuration (both are `auditLogConfigured: false` with no kind) and fires as well. Only the production view counts; a `[development]` block with `audit-log-to-console` changes nothing, and a production kind under `[production]` is taken as written.
  - A resource with `service: auditlog` of any type, a resource of type `org.cloudfoundry.existing-service` or `org.cloudfoundry.user-provided-service` whose name contains `audit` (case-insensitive), or a module requiring a resource named exactly `auditlog-ng` suppresses the finding. A `managed-service` resource that merely has `audit` in its name but a different `service`, and a module requiring a resource whose name only contains `auditlog-ng`, do not. The rule does not check that the server module actually lists the audit log resource in its `requires`, that the plan is `premium`, or that the instance exists in the target space.
  - `.cdsrc-private.json`, `.cdsrc.js`, `.env`, `default-env.json`, `CDS_CONFIG` and `CDS_*` environment variables, and `*.mtaext` extension descriptors are never read (they hold credentials), so a kind or a resource added only there is not seen.
  - The plugin's binding resolution was verified from the `cap-js/audit-logging` repository on GitHub (`package.json`: `audit-log-to-restv2` with `vcap.label: auditlog`, `audit-log-to-alsng` with `vcap.name: auditlog-ng`, `[production]` and `[hybrid]` defaulting to `audit-log-to-restv2`, `[development]` to `audit-log-to-console`; `srv/log2restv2.js`: the credentials check quoted above; `lib/access.js` and `lib/modification.js`: the lazy `cds.connect.to("audit-log")` with no error handling), the service name and plan from the SAP Help page "Audit Log Write API for Customers" through the `SAP-docs/btp-cloud-platform` GitHub mirror (`cf create-service auditlog premium <my-service-instance>`, `cf bind-service`), and the `org.cloudfoundry.existing-service` resource example (`my-auditlog-service`) from the CAP guide through the `cap-js/docs` mirror (`guides/security/dpp-audit-logging.md`, which installs the plugin with `npm add @cap-js/audit-logging`). What `cds add audit-logging` writes was verified from the `@sap/cds-dk` 10.2.0 package on the npm registry (`lib/init/template/audit-logging`): for Node.js only the `@cap-js/audit-logging` dependency (no `cds.requires.audit-log`), and in `mta.yaml` a resource `<app>-auditlog` of type `org.cloudfoundry.managed-service` with `service: auditlog` and `service-plan: premium` unless `--plan` says otherwise, inserted into the srv module's `requires`. `cap.cloud.sap` and `help.sap.com` do not resolve from the build environment, so the links are the canonical pages those sources publish to; the SAP Help link is the one both the plugin's README and the CAP guide give. The OWASP link follows the `A09_2025-Security_Logging_and_Alerting_Failures` entry in the OWASP/Top10 `2025/mkdocs.yml`.
