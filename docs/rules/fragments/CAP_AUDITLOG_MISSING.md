## CAP_AUDITLOG_MISSING

**Personal data is modelled but audit logging is not set up.** The CDS model holds personal data, declared with `@PersonalData` or recognisable from field names, but the project neither depends on the `@cap-js/audit-logging` plugin at runtime nor configures `cds.requires.audit-log` for production. CAP logs reads of sensitive data and changes of personal data only through that plugin (or a configured `audit-log` service), so without it nobody can tell afterwards who accessed which person's data, which data-protection regulations require and incident response depends on.

- **Data:** `packageJson.dependencies` and `devDependencies` (package names only), `cds.effective.production.auditLogConfigured` (whether `requires.audit-log` is present and not `false` in any shape, computed by the project collector from `.cdsrc.yaml`, `.cdsrc.json` and `package.json#cds` merged in cds order with `[production]` and `[production!]` blocks applied), and the CDS facts the collector keeps per `*.cds` file: entity names, element names, associations, and whether `@PersonalData` appears on an entity, one of its elements, or in an `annotate` statement. The rule reads them through the shared model helpers (`hasPersonalDataDeclared`, `effectiveEntities`, `personalEntities`), which resolve `using … as` aliases and namespace-qualified names.
- **Trigger:** `@sap/cds` is listed under `dependencies`, **and** the model holds personal data (`@PersonalData` is declared anywhere, or at least one entity is inferred to be personal: a strong field such as `email`, `phone`, `firstName`, `birthDate`, `iban`, `salary`, or weak address fields on an entity that links to a personal entity or is named like one), **and** neither `@cap-js/audit-logging` is listed under `dependencies` nor `requires.audit-log` is configured for production. One finding per project; the subject is the configuration key `requires.audit-log`.
- **Severity:** from the criticality matrix (the attacker needs an account or a foothold first; what the missing log costs is the ability to detect and reconstruct the access afterwards).
  - `high` = (`significant`, `advanced`): `@PersonalData` is declared, so the project knows it processes personal data and the plugin would log it generically as soon as it is added.
  - `medium` = (`moderate`, `advanced`): personal data is only inferred from field names; the annotations are missing as well (`CAP_PERSONAL_DATA_UNANNOTATED` reports those per entity).
  - The same two cells apply, with the title "Audit logging plugin is listed under devDependencies only, so it is inactive in production", when `@cap-js/audit-logging` appears under `devDependencies` but not under `dependencies`: `@sap/cds` fetches plugins from `devDependencies` only while `NODE_ENV` is not `production` (`lib/plugins.js`, `fetch(DEV = process.env.NODE_ENV !== 'production')`), and cds-dk's own `cds add audit-logging` test (`hasInProduction`) reads `dependencies` only, so the deployed app runs without the plugin.
  - `low` = (`minor`, `complex`), with the title "Audit logging uses the legacy client library; personal-data access is not logged automatically": `@sap/audit-logging` is listed under `dependencies` instead of the plugin. The project chose audit logging, but the legacy library offers a programmatic API only, so only the events the code logs explicitly are recorded; an attacker who wants to stay unnoticed first has to learn which paths the code logs, hence `complex`. This branch applies whether the personal data is declared or inferred, and takes precedence over a dev-only plugin.
- **Evidence:** `subject` (`requires.audit-log`), `personalDataDeclared` (boolean), `declaredEntities` (count of entities marked `@PersonalData` after merging `annotate` statements), `inferredEntities` (count of entities that look personal and carry no `@PersonalData`), `legacyLibrary` (boolean), `pluginInDevDependencies` (boolean), `impact`, `easeOfAttack`. Entity and field names are not repeated here; `CAP_PERSONAL_DATA_UNANNOTATED` names the inferred entities.
- **Location:** `package.json`, without a line: `cds add audit-logging` records the plugin there, so that is where the fix lands.
- **Remediation:** Add the `@cap-js/audit-logging` plugin with `cds add audit-logging`: it configures `cds.requires.audit-log` with console output in development and the SAP Audit Log service (`audit-log-to-restv2`) in production and, when the project has an `mta.yaml`, adds an `auditlog` resource (`org.cloudfoundry.managed-service`, service `auditlog`, plan `premium`) to it. Create an SAP Audit Log service instance (service `auditlog`, plan `premium`) in the target space and bind it to the app. The plugin logs only entities annotated with `@PersonalData`, so when the personal data is only inferred, annotate the personal entities first (`EntitySemantics` and `DataSubjectRole` on the entity; `FieldSemantics`, `IsPotentiallyPersonal` or `IsPotentiallySensitive` on the elements) and keep the annotations complete. When the plugin sits under `devDependencies`, move it to `dependencies`. With the legacy library, replace `@sap/audit-logging` by the plugin and keep the `auditlog` binding. Verify with `cds env requires.audit-log --profile production`.
- **References:** <https://cap.cloud.sap/docs/guides/security/dpp-audit-logging>, <https://cap.cloud.sap/docs/guides/security/dpp-annotations>, <https://owasp.org/Top10/2025/A09_2025-Security_Logging_and_Alerting_Failures/>
- **Limits / what does not trigger:**
  - Projects without `@sap/cds` under `dependencies` are not Node.js CAP apps and produce no finding (`cds init` puts `@sap/cds` there; CAP Java projects configure audit logging in `pom.xml`, which is not read, and get `requires.audit-log: true` in `.cdsrc.json` from `cds add audit-logging`, which the collector does see). A project that lists `@sap/cds` under `devDependencies` only is treated as a tooling or Java project and skipped.
  - A model without personal data, declared or inferred, produces no finding, whatever the dependencies. Entities with weak fields only (`city`, `postCode`, `country`, …) that neither link to a personal entity nor are named like one (`Warehouses`) do not count. The inference uses the field-name lists in `analyzers/project/patterns.ts`; a personal entity whose fields are named differently (`col1`, abbreviations, non-English names) is not recognised.
  - `@cap-js/audit-logging` under `dependencies`, or `requires.audit-log` configured for the production profile in any shape (`true`, a kind string, or an object; an explicit `false` does not count), suppresses the finding. The rule does not verify that the configured kind actually reaches the SAP Audit Log service, that the `handle` option still covers `READ` and `WRITE`, or that an `auditlog` instance is bound: `CAP_AUDITLOG_NOT_BOUND` checks the binding. A configuration under `[development]` only does not count. `@sap/audit-logging` under `devDependencies` only is ignored for the same reason the plugin is: it is not installed in production.
  - `.cdsrc-private.json`, `.cdsrc.js`, `.env`, `default-env.json`, `CDS_CONFIG` and `CDS_*` environment variables rank above the files read and are never opened (they hold credentials), so an `audit-log` configuration placed only there is not seen and the finding reflects the committed configuration only. The `CDS_PLUGINS` environment variable, which can register plugins outside `package.json`, is not seen either.
  - The CAP documentation pages were verified from the `cap-js/docs` GitHub mirror (`guides/security/dpp-audit-logging.md`, which documents the `audit-log-to-console`/`audit-log-to-restv2` presets, the `vcap.label: auditlog` binding, the `cds env requires.audit-log --profile production` command and the `auditlog` service with plan `premium`; and `guides/security/dpp-annotations.md`; both are listed under `guides/security/_menu.md` and `.vitepress/rewrites.js` does not rename them) because `cap.cloud.sap` does not resolve from the build environment; the links are the canonical pages those files publish to. The former `guides/data-privacy/*` paths no longer exist in the mirror. What `cds add audit-logging` writes was read from the `@sap/cds-dk` package (`lib/init/template/audit-logging`: `@cap-js/audit-logging` under `dependencies` for Node.js, `requires.audit-log: true` for Java, and the `mta.yaml` resource with `service-plan` defaulting to `premium`). That `@sap/audit-logging` is the legacy client library is taken from the design review facts and the npm registry (`@sap/audit-logging`: "Provides audit logging functionalities for Node.js applications", no CDS integration); the SAP Help page on the Audit Log Write API that the CAP guide links to could not be verified and is therefore not listed. The OWASP link follows the `A09_2025-Security_Logging_and_Alerting_Failures` entry in the OWASP/Top10 `2025/mkdocs.yml`.
