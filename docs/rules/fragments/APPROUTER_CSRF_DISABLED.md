## APPROUTER_CSRF_DISABLED

**An authenticated approuter route has CSRF protection switched off.** The application router checks an `x-csrf-token` header on every state-changing request (PUT, POST, PATCH, DELETE) to a route that requires a login, and answers 403 without it. A route with `"csrfProtection": false` skips that check, so a page on another site can make the browser of a logged-in user send a write request to the backend with the user's session cookie attached: cross-site request forgery, which OWASP lists under A01 Broken Access Control (CWE-352).

- **Data:** every `xs-app.json` found by the walk (`xsApps`): the top-level `authenticationMethod`, and for each route its `source`, `authenticationType`, `csrfProtection` and which of `destination`, `service` or `localDir` it names. The destination name is not stored, only a hint computed from it. `scope`, `target`, `httpMethods`, `cacheControl`, `identityProvider` and every other route property are never read.
- **Trigger:** a route with an explicit `"csrfProtection": false` that forwards to a `destination`, whose `authenticationType` is not `none`, in a file whose `authenticationMethod` is not `none`. A missing `authenticationType` counts as authenticated: the router then picks `xsuaa` or `ias` from its service bindings. One finding per route source per project (the first file in name order when the same source is disabled in several files); the subject is the route `source` as written.
- **Severity:** from the criticality matrix, both inputs recorded in the evidence.
  - `medium` (impact `moderate`, ease of attack `advanced`), always: the attacker needs a victim who is logged in and visits a page they control, and the damage is limited to what that user may already do; the request goes through with the user's authorization, not beyond it.
- **Evidence:** `subject` (route source), `authenticationType` (`xsuaa`, `ias`, `basic`, `other` or `null` when the route leaves it to the bindings), `authenticationMethod` (`route`, `other` or `null`), `targetHint` (`api`, `ui5-cdn`, `html5-repo` or `other`, computed from the destination name), `routes` (count of routes in the file), `files` (count of xs-app.json files that disable CSRF protection on this source), `impact`, `easeOfAttack`.
- **Location:** the `xs-app.json` file; no line, since the collector keeps route facts only.
- **Remediation:** Remove `"csrfProtection": false` from the route in xs-app.json (the default is `true`), so the application router rejects PUT, POST, PATCH and DELETE requests that carry no valid `x-csrf-token` header. Clients obtain the token with a GET or HEAD request that sends `x-csrf-token: fetch`; the SAPUI5 OData models and the CAP Fiori preview do this on their own. If the route only ever serves GET and HEAD, CSRF protection costs nothing, so there is no reason to switch it off. If `cds add app-frontend` generated the route, set the flag back to `true` after generating.
- **References:** <https://help.sap.com/docs/btp/sap-business-technology-platform/routes>, <https://help.sap.com/docs/btp/sap-business-technology-platform/application-router-configuration>, <https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html>, <https://owasp.org/Top10/2025/A01_2025-Broken_Access_Control/>
- **Limits / what does not trigger:**
  - A route without `csrfProtection`, or with `csrfProtection: true`, produces nothing: the application router's default is `true` (SAP Help, "Routes": "Toggle whether this route needs CSRF token protection. The default value is “true”.").
  - A public route (`authenticationType: none`) and every route in a file with `authenticationMethod: none` produce nothing, because the router applies CSRF protection only to routes that require a login (SAP Help, "Application Router Configuration", CSRF Protection: "A path is considered public, if it does not require authentication. This is the case for routes with `authenticationType: none` or if authentication is disabled completely via the top level property `authenticationMethod: none`"). Whether such a route should be public at all is the subject of `APPROUTER_ROUTE_NO_AUTH`.
  - Routes to a `service` (for example `html5-apps-repo-rt`) or a `localDir`, and routes naming none of the three targets, are not reported, following the design table: the flag matters where state-changing requests reach a backend through a destination. A `service` route that proxies writes to a reused service instance is therefore not seen.
  - `cds add app-frontend` generates `"csrfProtection": false` on the OData route of the xs-app.json it writes; the finding is intended there and the remediation applies as it stands. Routes generated by `cds add approuter` carry no such flag and do not trigger.
  - The rule does not know which HTTP methods the route accepts: a route that lists only `GET` and `HEAD` under `httpMethods` is still reported, since the collector does not read that property; the flag can simply be removed there.
  - When the same route source is disabled in several `xs-app.json` files of one repository, only one finding is produced, located in the first file by name, with `files` counting the others. `xs-app.json` files under skipped directories (`node_modules`, `gen`, `dist`, dot-directories) are never read, and a `*.mtaext` extension descriptor cannot change routes.
