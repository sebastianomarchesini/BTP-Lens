## APPROUTER_ROUTE_NO_AUTH

**An approuter route hands requests to a backend without a login.** A route in `xs-app.json` with `authenticationType: none` forwards every request to its `destination` or `service` as it arrives: no session, no token, no user. Whatever that backend serves is reachable by anyone who can reach the approuter, and the backend receives no identity it could use for its own checks. When the whole file sets `authenticationMethod: none`, this applies to every route in it.

- **Data:** every `xs-app.json` of the project (`xsApps`): its top-level `authenticationMethod`, and per route the `source` pattern as written, `authenticationType`, which of `destination`/`service`/`localDir` is set, a hint derived from the destination or service name (`ui5-cdn`, `html5-repo`, `api`, `other`; the name itself is not kept) and whether the source matches `logout.logoutPage`. Destination names, `csrfProtection`, `scope`, `cacheControl` and every other property are not used by this rule.
- **Trigger:**
  - a file whose `authenticationMethod` is `none`: one finding per file, the subject is the file path; the routes of such a file are not reported separately, since the file-level setting already covers them;
  - otherwise a route with `authenticationType: none` whose target is a `destination` or a `service`, unless its source (after a leading `^`) starts with `/-/cds/` or `/mt/`, its target hint is `ui5-cdn`, or it is the logout page. One finding per source per project; within a file the first route with that source counts (the approuter uses the first match), across files the API-like occurrence wins, otherwise the first file in path order. The subject is the route source as written.
- **Severity:** from the criticality matrix, both inputs recorded in the evidence. No login is needed in any branch, so the ease of attack is always `easy`.
  - `high` (impact `moderate`, ease of attack `easy`) when the whole file disables authentication, when the destination or service name hints at an API (`srv`, `api`, `backend`), or when the source matches `/odata|\/api|\/rest|\/srv|\/v\d+|graphql/i`: data endpoints are open. (The design table paired this branch with impact `significant`, which the matrix maps to `critical`; the named severity `high` was kept and the impact lowered, because a CAP or Java backend usually still validates the token itself, so the approuter is one of two layers.)
  - `medium` (impact `minor`, ease of attack `easy`) for every other forwarded route: the target looks like static or HTML5 content, but it is still served without a session and the destination may hide more than that.
- **Evidence:** for a route: `subject` (route source), `target` (`destination` or `service`), `targetHint`, `apiLike` (whether the hint or the source pattern decided `high`), `exemptedRoutes` (count of unauthenticated forwarding routes of the same file that the exemptions silenced), `files` (count of xs-app.json files in which this source forwards without authentication), `impact`, `easeOfAttack`. For a file: `subject` (file path), `authenticationMethod` (`none`), `routes` (count), `impact`, `easeOfAttack`.
- **Location:** the `xs-app.json` file; no line, since the collector keeps route properties only.
- **Remediation:** Remove `authenticationType: none` from the route, or set it to `xsuaa` (or `ias` when the approuter is bound to Identity Authentication), so the approuter forwards only requests with a valid session and passes the user token to the backend. Keep `none` only for routes that serve public static content from a `localDir` or the UI5 CDN, and for the logout page. If the destination must stay reachable without a login, make sure the backend enforces its own authentication and does not trust the approuter to have done it. For a file with `authenticationMethod: none`, set it to `route` (or remove the property; `route` is the default) so that each route decides with its own `authenticationType`.
- **References:** <https://help.sap.com/docs/btp/sap-business-technology-platform/routes>, <https://help.sap.com/docs/btp/sap-business-technology-platform/routing-configuration-file>, <https://owasp.org/Top10/2025/A07_2025-Authentication_Failures/>
- **Limits / what does not trigger:**
  - Only an explicit `authenticationType: none` counts. A route without the property inherits the approuter default (`xsuaa` or `ias`, chosen from the service bindings), and `basic`, `other` and unknown values are not reported. A file without `authenticationMethod` authenticates per route.
  - Routes that serve local files (`localDir`) and routes with no recognisable target are never reported, whatever their authentication type: static content is commonly public, and the rule is about backends.
  - The MTX routes that `cds add approuter` generates (`^/-/cds/.*` for Node.js, `^/mt/.*` for Java) carry `authenticationType: none` by design, because the multitenancy APIs authenticate the SaaS provisioning service themselves; they are exempt. A source that merely contains `/-/cds/` further in (for example `^/app/-/cds/(.*)$`) is not exempt.
  - A route to the UI5 CDN (destination name `ui5`, or containing `sapui5` or `cdn`) and the route that matches `logout.logoutPage` are exempt: SAP documents both with `authenticationType: none`. Whether the UI5 bootstrap itself is safe is the subject of `UI5_BOOTSTRAP_EXTERNAL`.
  - A file with `authenticationMethod: none` produces one finding for the file and none for its routes, so the count of findings is not the count of open endpoints; the `routes` evidence gives that.
  - The same source in several `xs-app.json` files yields one finding (the API-like occurrence, otherwise the first file in path order) with `files` saying how many files carry it; fixing one file moves the finding to the next.
  - The rule does not know what the destination serves. A destination to a backend that enforces its own JWT check is still reported, because the approuter no longer attaches a token and the backend becomes the only line of defence; the `apiLike` evidence and the `high`/`medium` split are heuristics on names and paths, not a probe. Destinations defined only in the subaccount, `xs-app.json` files under skipped directories (`node_modules`, `gen`, `dist`, dot-directories) and `*.mtaext` overrides are never read.
  - `csrfProtection` on an unauthenticated route is irrelevant (CSRF protection applies only to non-public routes) and is not reported here; see `APPROUTER_CSRF_DISABLED` for authenticated routes.
  - The SAP Help pages were verified through the `SAP-docs/btp-cloud-platform` GitHub mirror (`docs/30-development/routes-666eb55.md`: "`none`: No authentication is required for the route", and the default "If you do not define the `authenticationType`, the application router selects the authentication method based on its service bindings"; `docs/30-development/routing-configuration-file-c103fb4.md`: `authenticationMethod` is "The method used to authenticate user requests, for example: “route” or “none” (no authentication)"; `docs/30-development/logout-2296b4d.md`: the logout page route "must be set to `none`"). `help.sap.com` does not resolve from the build environment, so the links are the canonical pages those files publish to. The MTX route shapes come from the design review of `cds add approuter` output. The OWASP link follows the `A07_2025-Authentication_Failures` entry in the OWASP/Top10 `2025/mkdocs.yml`.
