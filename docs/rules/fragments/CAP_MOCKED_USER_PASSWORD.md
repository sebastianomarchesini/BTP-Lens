## CAP_MOCKED_USER_PASSWORD

**Mocked users are defined with a password in a project configuration file.** The `mocked` and `basic` authentication strategies take their users from `cds.requires.auth.users`, where each user may carry a `password`. A password in `package.json` or `.cdsrc.json` travels with every clone, every fork and every CI log, and people reuse passwords, so it is worth more to an attacker than the local login it protects.

- **Data:** `cds.effective.<view>.mockedUsersWithPassword` and `mockedUsers` for the `development` and `production` views, computed by the project collector from `.cdsrc.yaml`, `.cdsrc.json` and `package.json#cds` merged in cds order with `[development]`/`[production]` (and `[…!]`) blocks applied at every nesting level. The collector counts the keys of `requires.auth.users` and how many of them have a `password` key; it never reads the user names, the passwords, roles or attributes. `sourcesRead` records which of the three files existed.
- **Trigger:** `mockedUsersWithPassword > 0` in the development or the production view. One finding per project; the subject is the configuration key `requires.auth.users`. When both views carry passwords, the finding reports the production view (the one reachable from the deployed app).
- **Severity:** from the criticality matrix, ease of attack `complex` in both cases (the attacker needs read access to the repository or a build artifact first).
  - `medium` = (`moderate`, `complex`): the **production** view has users with passwords and `CAP_MOCKED_AUTH_IN_PROD` does not fire (production auth is unset, `jwt`, `xsuaa`, `ias`, `ams` or another real strategy). The users are dead configuration in production, but the passwords are published.
  - `low` = (`minor`, `complex`): otherwise. Either the passwords exist only in the **development** view, where they protect nothing beyond a local login, or production auth is `mocked`, `dummy` or `basic`, in which case `CAP_MOCKED_AUTH_IN_PROD` already reports the impersonation risk as `critical` and this finding only adds the password hygiene point.
- **Evidence:** `subject` (`requires.auth.users`), `view` (`development` or `production`), `usersWithPassword` (count), `mockedUsers` (count), `authKind` (the view's strategy, or null), `impact`, `easeOfAttack`. The title names the view.
- **Location:** the source read that cds applies last (`package.json`, else `.cdsrc.json`, else `.cdsrc.yaml`), without a line. No location when none of the three files existed.
- **Remediation:** Delete the `password` values from the mocked users in `cds.requires.auth.users` and keep the `users` block under `[development]` only, so it never applies to production. A developer who needs a password-protected local login can define it in `.cdsrc-private.json`, which cds reads but which must stay out of version control. If any of these passwords was ever reused on another system, change it there.
- **References:** <https://cap.cloud.sap/docs/node.js/authentication#mocked>, <https://cap.cloud.sap/docs/node.js/cds-env>, <https://owasp.org/Top10/2025/A07_2025-Authentication_Failures/>
- **Limits / what does not trigger:**
  - Mocked users without a `password` key do not trigger, whatever their number, and neither does a project with no `users` block. A `mocked`, `dummy` or `basic` production strategy on its own is the subject of `CAP_MOCKED_AUTH_IN_PROD`, not of this rule.
  - The pre-defined users that `@sap/cds` ships (`alice`, `bob`, …) are built-in defaults, not project configuration, and are not counted.
  - `.cdsrc-private.json`, `.cdsrc.js`, `.env`, `default-env.json`, `CDS_CONFIG` and `CDS_*` environment variables rank above the files read and are never opened (they hold credentials), so passwords defined only there are not seen and the finding reflects the committed configuration only.
  - The rule does not know whether a password is weak, strong, or a placeholder: any `password` key counts. It also does not check `.gitignore`: a `package.json` is always treated as committed.
  - The location names the highest-priority file that existed, not necessarily the one that defines the users; the collector does not record which source won the merge.
  - The CAP documentation pages were verified from the `cap-js/docs` GitHub mirror (`node.js/authentication.md`, heading "Mocked Authentication" with anchor `mocked`, and `node.js/cds-env.md`) because `cap.cloud.sap` does not resolve from the build environment; the links are the canonical pages those files publish to. The OWASP link follows the `A07_2025-Authentication_Failures` entry in the OWASP/Top10 `2025/mkdocs.yml`.
