## CAP_SERVICE_NO_RESTRICTION

**A served CDS service has no access control at all.** Neither the service nor any of its entities or actions carries `@requires` or `@restrict`, in the definition or in an `annotate` statement. CAP adds an implicit `@requires: 'authenticated-user'` to such services in production, so every user who can log in can read, and unless an entity is `@readonly`, change its data. When the production profile sets `restrict_all_services: false` or a development authentication strategy, that implicit requirement is gone and the service answers anonymous requests too.

- **Data:** the effective services of the project (`effectiveServices` in `analyzers/project/cdsModel.ts`): every `service` found in `*.cds` files with its entities and actions, merged with `@requires`/`@restrict.to` from `annotate` statements that target the service, `Service.Entity` or `Service.action` (by exact name, `using … as` alias or namespace-qualified suffix), plus `@protocol: 'none'` and `@cds.external` markers; `cds.effective.production.restrictAllServices` and `cds.effective.production.authKind` from the merged cds configuration.
- **Trigger:** a service whose merged `requires` and `restrictTo` are both empty, that is not `@protocol: 'none'`, not `@cds.external`, and whose file is not under `srv/external/`. One finding per service name per project (the first declaration in file order when a name appears twice); the subject is the service name.
- **Severity:** from the criticality matrix, both inputs recorded in the evidence.
  - `critical` (impact `severe`, ease of attack `easy`) with the title "Service is open to everyone" when the production profile sets `restrict_all_services: false` or its authentication strategy is `mocked`, `dummy` or `basic`: nobody has to log in.
  - `high` (impact `significant`, ease of attack `advanced`) when at least one entity is not `@readonly` or the service has an action or function: any authenticated user can change data or trigger logic, but needs an account first. (The design table paired this branch with ease `easy`, which the matrix maps to `critical`; the named severity `high` was kept and the ease input adjusted to match it.)
  - `medium` (impact `moderate`, ease of attack `advanced`) when every entity is `@readonly` and there are no actions, including a service with no entities: any authenticated user can read everything, but not change it.
- **Evidence:** `subject` (service name), `restrictAllServices` (production value, `null` when unset), `authKind` (production value, `null` when unset), `entities`, `writableEntities` and `actions` (counts), `impact`, `easeOfAttack`.
- **Location:** the `.cds` file and the line of the `service` keyword.
- **Remediation:** Restrict the service with `@requires`, for example `service AdminService @(requires: 'admin') { ... }`, using a role that `xs-security.json` defines as a scope and role template, and add `@restrict` rules on entities or actions that need finer control (`@restrict: [{ grant: 'READ', to: 'viewer' }]`). Mark data that must never be changed through the service with `@readonly`. A service that is only consumed in-process should declare `@protocol: 'none'`. If the service must stay open to every authenticated user, say so explicitly with `@requires: 'authenticated-user'`. When the production profile sets `restrict_all_services: false` or a development authentication strategy, remove that as well, since it lets unauthenticated callers in.
- **References:** <https://cap.cloud.sap/docs/guides/security/authorization>, <https://cap.cloud.sap/docs/node.js/authentication>, <https://owasp.org/Top10/2025/A01_2025-Broken_Access_Control/>
- **Limits / what does not trigger:**
  - Any explicit restriction counts, including a pseudo-role: `@requires: 'authenticated-user'` or `@requires: 'any'` is a documented decision, not a missing one, and produces no finding. Whether the roles used exist in XSUAA is the subject of `CAP_ROLE_NOT_IN_XSUAA`.
  - A restriction on a single entity or action silences the rule for the whole service, because the author has evidently thought about access control there; the rule does not report the remaining unrestricted members.
  - Internal services (`@protocol: 'none'`), imported remote services (`@cds.external`) and anything under a `srv/external/` directory are skipped. A file whose name merely contains `external` (for example `srv/externalCatalog.cds`) is not.
  - `restrict_all_services` and the authentication strategy come from `.cdsrc.yaml`, `.cdsrc.json` and `package.json#cds` only; `.cdsrc-private.json`, `.cdsrc.js`, `.env` and `CDS_*` environment variables are never read and can change the result at runtime (see `CAP_MOCKED_AUTH_IN_PROD`). The development profile is ignored.
  - Annotations are matched by name. An `annotate` that reaches the service only through an `extend`, a model imported from `node_modules`, or a build-time plugin is not seen, so such a service is reported although it is restricted at runtime. Services generated by CAP itself (for example `cds.xt.*` MTX services) are not in the project's `.cds` files and are never reported.
  - `@readonly` is detected on the service entity only; a projection that is read-only because its source is a view, or because of `@insertonly`/`@Capabilities` annotations, still counts as writable.
  - The CAP pages were verified from the `cap-js/docs` GitHub mirror (`guides/security/authorization.md`, which states that by default CDS services have no access control and that authenticated users then have access to all entities, and `node.js/authentication.md`, which documents `restrict_all_services`) because `cap.cloud.sap` does not resolve from the build environment; the links are the canonical pages those files publish to. The OWASP link follows the `A01_2025-Broken_Access_Control` entry in the OWASP/Top10 `2025/mkdocs.yml`.
