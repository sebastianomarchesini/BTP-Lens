# Pre-release audit of 0.1.0 (2026-10-11)

Record of the multi-agent audit run on the release branch before tagging `v0.1.0`. Eleven independent auditors each reviewed one dimension of the release at commit `8408dd0`; a dedup pass merged their findings; every non-cosmetic finding was then judged by three adversarial verifiers (reproduce, refute, impact), a finding counting as confirmed when at least two of the three found it real; a completeness critic named four areas nobody had covered and four more auditors went through them, with the same verification. The fixes for the first round landed in commit `9d5199d` on the release branch; the findings of the gap pass are recorded here for the next round.

## Numbers

- First round: 75 raw findings from 11 auditors; 59 unique after dedup (47 non-nit, 12 nits). Verification: 46 confirmed, 1 refuted.
- Gap pass (scale-and-data-edge-cases, clean-room-release-rebuild, report-accessibility-axe, proxy-and-windows-paths): 21 new non-nit findings, 21 confirmed, 0 refuted, plus 1 nits.
- Consensus severity of everything confirmed: 0 blocker, 2 high, 9 medium, 47 low, 9 nit.
- Of the confirmed first-round findings, 36 are fixed in `9d5199d`, 0 partly, 2 left on purpose, 2 need an owner action and 6 are open.

## Next round (for 0.1.0 or 0.1.1, in this order)

## Gap pass

The completeness critic asked what would still embarrass the release that nobody had checked, and named these areas:

- **scale-and-data-edge-cases:** Auditors tested pagination, droplet-less apps and stopped apps on small fixtures only. Nobody exercised hundreds of apps and spaces, long query strings, non-ASCII names, future-dated timestamps or clock skew, or how the UI and the CSV behave with that data.
- **clean-room-release-rebuild:** Everything audited used the pre-built dist and tarball in the working tree. Nobody rebuilt from a clean checkout with `npm ci`, nobody ran the CI coverage step (85 percent analyzer threshold) or the repo's own Playwright e2e, and nobody compared a clean-room tarball to the one that will be published.
- **report-accessibility-axe:** The ui-report audit checked keyboard flow, roles and labels by inspection but never ran an automated or structured accessibility audit; the build prompt makes accessibility a stated requirement (screen-reader labels, keyboard navigation) and severity is conveyed by color.
- **proxy-and-windows-paths:** The README documents a corporate proxy workaround (NODE_USE_ENV_PROXY, NODE_EXTRA_CA_CERTS) but nobody exercised a real proxy path with the CLI. Windows behaviour was only argued from source, and cmd quoting, CRLF, Windows cf config location and path handling in output names were not run or statically traced end to end.

### Gap-pass claims, evidence and proposed fixes

#### proxy-and-windows-paths-0 · consensus low · A proxy URL without a scheme or with a bad port crashes every command with a raw Node stack trace; with credentials in the URL the proxy password is printed. Exit code is 1.

- File: `README.md`:55 · auditor confidence 0.9
- Claim: README tells users to set NODE_USE_ENV_PROXY=1 and HTTPS_PROXY but never says the value needs the http:// prefix. A common Windows form such as proxy.corp:8080 makes Node abort at startup, before any BTP Lens code runs, so even `version` and `--help` fail. If the URL carries user:password and is malformed, Node's error dumps the full URL including the password. Exit code 1 collides with BTP Lens's 'findings met --fail-on' code (2 means tool error).
- Evidence: env -i HTTPS_PROXY=proxy.corp:8080 NODE_USE_ENV_PROXY=1 node dist/cli.js version -> 'InvalidArgumentError: Invalid URL protocol: the URL must start with http: or https:' at setupHttpProxy (pre_execution:202), exit=1. HTTPS_PROXY=http://alice:SECRETPW@proxy.corp:99999 ... version -> 'TypeError: Invalid URL ... code: ERR_INVALID_URL, input: http://alice:SECRETPW@proxy.corp:99999' (password in output, grep -c SECRETPW = 1 on doctor too), exit=1. socks5://... gives the same InvalidArgumentError. Node 22.22.0 (simulated with local dummy values only).
- Proposed fix: Document the exact accepted form (http://user:pass@host:port, no socks, URL-encode special characters) next to the NODE_USE_ENV_PROXY line, and warn that a malformed value prints the password. Optionally validate HTTPS_PROXY/https_proxy in cli.ts before any import runs (note: the crash happens in Node's pre-execution, so only a launcher wrapper or documentation can help; the check in doctor cannot run).
- Verifier (impact) on the fix: Only the documentation change is needed.
