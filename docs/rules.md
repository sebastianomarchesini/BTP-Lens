# Rules

Every finding has a stable rule id, a severity, the evidence that triggered it, a concrete remediation and reference links. Rules are pure functions of the collected data. They use the **scan time** as "now", so `btp-lens report --from snapshot.json` gives the same result offline. The data behind each rule, and its limits, are recorded in [data-sources.md](data-sources.md).

Every rule carries one or more [OWASP Top 10 (2025)](https://owasp.org/Top10/2025/) categories. They appear as `owasp/<id>` tags in the SARIF output and next to the rule in the HTML report.

## Criticality

New rules derive their severity from a fixed matrix of **impact** (what an attacker gains, or what is lost) and **ease of attack** (what an attacker needs first). The matrix is the one used in the public SAP TechEd 2026 workshop XP261 ("From Code to Compliance"), so a reader of that material gets the same severities here (`packages/cli/src/model/criticality.ts`, covered cell by cell by a unit test):

| impact \ ease of attack | very-complex | complex | advanced | easy |
| --- | --- | --- | --- | --- |
| **severe** | high | high | critical | critical |
| **significant** | medium | medium | high | critical |
| **moderate** | low | medium | medium | high |
| **minor** | low | low | medium | medium |

- *ease of attack*: `easy` needs nothing (an anonymous request, a public user name); `advanced` needs an account or a foothold; `complex` needs read access to the repository, a build artifact or a database copy first; `very-complex` needs several of those together.
- *impact*: `severe` is full impersonation or unauthenticated access to everything; `significant` is data change or financial data in clear text; `moderate` is bounded data exposure or a lost control (logging, retention, CSRF); `minor` is hygiene or drift that pays off only combined with other mistakes.

Whenever a rule used the matrix, the finding's evidence carries the two inputs as `impact` and `easeOfAttack`, so the severity can be checked by hand. Where the rule descriptions below name the two inputs, they are the ones the code uses; several `low` cells are `minor` × `complex` because `minor` × `advanced` is `medium` in the matrix. The Cloud Foundry rules of 0.1.0 keep their threshold-based severities.

## Which rules run

A scan records every rule it considered in `checks[]`, next to the collectors:

- A rule is **omitted** from a scan when none of its collectors is part of that scan: the project rules are not listed in a Cloud Foundry scan, and the Cloud Foundry rules are not listed in a project scan. They are not checks of that scan.
- A rule is recorded as **skipped** (`dependency_skipped`) when its collector was part of the scan but did not run, for example after a 403 or a collector error. The reader then knows what was not looked at; "no findings" is never the same as "not checked".
- Otherwise the rule is recorded as `ran`, with or without findings.

`btp-lens report --from` re-runs the rules on a snapshot and applies the same two conditions to the checks stored in it, so a snapshot from a Cloud Foundry scan never gains project rules by being reanalysed, and the reverse.

## Risk score

Apps are ranked by a weighted sum of their findings: critical 100, high 25, medium 5, low 1, info 0. A single critical finding outranks any number of lower ones in practice. A score of 0 means that no rule matched; it does not mean the app is safe. A project scan ranks its findings the same way, under the project's name.

## APP_NO_RECENT_DEPLOY

**Last deploy older than 12 months.** The app still runs with the libraries, buildpack and runtime from when its current droplet was staged, so fixes released since then are missing.

- **Data:** the current droplet's `created_at` (`GET /v3/droplets?current=true`).
- **Severity:**
  - `low`: the droplet is more than 365 days old.
  - `medium`: it is more than 730 days old.
  - Apps that were never staged have no droplet and produce no finding.
- **Evidence:** `lastDeployAt`, `ageDays` and `thresholdDays`.
- **OWASP:** A03:2025 Software Supply Chain Failures (the category that absorbed "Vulnerable and Outdated Components").
- **Remediation:** Update the app dependencies and redeploy (`cf push`), or restage (`cf restage`) to pick up the current buildpack and runtime patches. If the app is no longer needed, delete it.
- **References:** <https://docs.cloudfoundry.org/devguide/deploy-apps/start-restart-restage.html>
- **If the droplet collector is skipped** (for example after a 403), the rule is recorded as skipped and produces no findings.

## RUNTIME_NODE_EOL / RUNTIME_JAVA_EOL

**The runtime version is past, or within 90 days of, its end of life.**

- **Data:**
  - The Node.js or Java version comes from the droplet's detected buildpacks.
  - EOL dates come from endoflife.date: `nodejs`, and for Java `sapmachine` (SAP Java buildpack) or `eclipse-temurin`.
- **Severity:**
  - `high`: past end of life.
  - `medium`: end of life within 90 days.
  - An unknown version produces no finding and is shown as "unknown" in the inventory.
- **Evidence:** runtime, version, release cycle, `eolFrom` and days until or since EOL.
- **Remediation:** Move to a supported release line (named in the finding), then restage.

## DEP_KNOWN_CVE

**A dependency in the SBOM has a known vulnerability.** The SBOM is built locally with `btp-lens sbom` from `package-lock.json`, `pom.xml` or `mta.yaml`.

- **Data:** OSV.dev `POST /v1/querybatch`, then `GET /v1/vulns/{id}` for severity.
- **Severity:** from the highest CVSS base score.
  - `critical`: 9.0 or higher.
  - `high`: 7.0 to 8.9.
  - `medium`: 4.0 to 6.9.
  - `low`: under 4.0.
  - `medium` when the advisory has no score.
- **Evidence:** package, version, advisory ids and aliases, and the fixed version if known.
- **Remediation:** Upgrade the package to the fixed version named in the advisory.

## APP_IDLE

**The app is stopped for a long time, or runs with no sign of use.**

- **Data:** app `state` and `updated_at`, droplet and process timestamps, plus app usage and audit events.
- **CF limit:** CF keeps events for **31 days** by default, so "no events in 180 days" cannot be proven from events alone. The evidence names the window that was checked.
- **Severity:** `low`.
  - Stopped, with `updated_at` more than 90 days ago.
  - Or running, with droplet and process unchanged for more than 180 days **and** no events in the retention window.
- **Remediation:** Confirm that the app is still needed; delete it or its route if not.

## UI5_OUT_OF_MAINTENANCE

**The SAPUI5 version served by the app is out of maintenance.**

- **Data:**
  - One unauthenticated `GET` of `resources/sap-ui-version.json` on the app's route, with a 5 s timeout and redirects not followed. Turn it off with `--no-probe-routes`.
  - The maintenance status comes from `ui5.sap.com/versionoverview.json`.
- **Severity:**
  - `medium`: out of maintenance.
  - `high`: past end of cloud provisioning.
  - Apps behind a login redirect, or that load UI5 from the CDN, are shown as "unknown".
- **Remediation:** Move the app to a maintained UI5 version (a long-term maintenance release if possible).

## BUILDPACK_OUTDATED

**The droplet was built with an older buildpack than the platform currently offers.**

- **Data:**
  - The droplet buildpack `version`, compared with `/v3/buildpacks`.
  - That endpoint has **no version field**, so the version is parsed from `filename`.
  - When parsing fails, the rule compares dates instead, and says so in the evidence.
- **Severity:**
  - `medium`: older version.
  - `low`: date comparison only.
- **Remediation:** `cf restage` the app to build it with the current buildpack.

## STACK_DEPRECATED

**The app runs on a deprecated stack** (for example `cflinuxfs3`).

- **Data:**
  - The stack `state` from `/v3/stacks`.
  - If a Cloud Controller does not report `state`, a built-in list is used, marked as such in the evidence.
- **Severity:**
  - `high`: `DEPRECATED` or `DISABLED`.
  - `medium`: `RESTRICTED`.
- **Remediation:** Push the app to the current stack (`cf push -s cflinuxfs4`) and test it.

## SAP_PKG_OUTDATED

**`@sap/cds`, `@sap/approuter`, `@sap/xssec` or `@sap/xsenv` is behind the current major version.**

- **Data:** versions from the SBOM, compared with `dist-tags.latest` from the npm registry. Only these four packages are queried.
- **Severity:**
  - `medium`: one major version behind.
  - `high`: two or more behind.
- **Remediation:** Upgrade to the current major version, following the package's migration guide.

## ENV_SECRET_PLAINTEXT

**An environment variable whose name looks like a secret is set directly on the app** instead of coming from a service binding.

- **Data:**
  - Keys from `GET /v3/apps/:guid/environment_variables`, which returns only user-provided variables.
  - This rule runs only with `--deep`, because Space Auditor cannot read environment variables.
  - Values are discarded when they are read, and only the **name** is reported.
- **Severity:** `high`.
- **Remediation:** Move the value into a service binding or a user-provided service, and rotate the secret.
- **Side effect:** CF records `audit.app.environment_variables.show` for each app that is read (see [privacy.md](privacy.md)).

## Project rules

`btp-lens project --path <dir>` scans a local CAP or MTA project: it reads an allow-list of project files (configuration, descriptors, CDS models, seed CSV headers and HTML pages) from the file system, with no network access, no child processes and no `git` call, and applies the thirteen rules below. What is read, what is never read and the parser limits are in [data-sources.md](data-sources.md#8-local-project-files-btp-lens-project); what is kept from the files is in [privacy.md](privacy.md#project-scans).

The rules translate the OWASP Top 10 (2025) patterns of the public SAP TechEd 2026 workshop **XP261 "From Code to Compliance"** (<https://github.com/SAP-samples/teched2026-XP261>, Apache-2.0) into deterministic, evidence-backed checks: no AI, no code execution, no exploitation, the same result on every run and offline with `report --from`. BTP Lens is an independent open-source project and is **not affiliated with, endorsed by or sponsored by SAP SE**; the workshop is cited as the source of the patterns and of the criticality matrix, nothing more.

Every project finding carries `evidence.subject` (the service, entity, role, scope, route source, file or column it is about), the two matrix inputs, and a `location` (file, and line where the parser knows it) that the SARIF output turns into a code-scanning annotation. Each rule yields one finding per subject per project. Evidence never contains a value copied from the project other than identifiers, counts, booleans and relative file names; the `.cdsrc-private.json`, `.cdsrc.js`, `.env`, `default-env.json`, `*.mtaext` and `CDS_*` sources are never opened, so every rule reflects the committed configuration and says so in its limits. The links in the references are the canonical SAP, CAP and OWASP pages; because `cap.cloud.sap`, `help.sap.com`, `ui5.sap.com` and `owasp.org` do not resolve from the build environment, each section records which GitHub mirror of the page was read to verify it.

The synthetic fixture `packages/cli/test/fixtures/projects/acme-incidents` triggers every project rule at least once, and `clean-cap` triggers none; `packages/cli/test/e2e/project.test.ts` pins the exact list of findings for both.

## CAP_MOCKED_AUTH_IN_PROD

**A development authentication strategy is configured for production.** The effective CAP configuration for the `production` profile selects `mocked`, `dummy` or `basic` authentication. With `mocked`, the pre-defined mock users shipped with `@sap/cds` (four fixed user names, one of them with the `admin` role) are merged into the project's `users`, and the default `"*": true` entry accepts any other login as well, unless the project overrides them; with `basic`, the users listed in the project files are accepted (the pre-defined ones are off). `dummy` accepts every request and switches `@requires` and `@restrict` off, and `mocked` in production also switches off the implicit `@requires: 'authenticated-user'` on unannotated services. CAP itself defaults to `jwt` in production, so this only happens when the project sets it.

- **Data:** `cds.effective.production.authKind`, computed by the project collector from `.cdsrc.yaml`, `.cdsrc.json` and `package.json#cds` merged in cds order, with `[production]` and `[production!]` blocks applied at every nesting level; `requires.auth` as a string or `requires.auth.kind`. `sourcesRead` records which of the three files were read and parsed and carried a cds configuration (`package.json` only when it has a `cds` key); a file that exists but is unreadable or malformed is listed under `unreadable` instead and does not appear.
- **Trigger:** `authKind` is `mocked`, `dummy` or `basic`. One finding per project; the subject is the configuration key `requires.auth`.
- **Severity:** `critical`, from the criticality matrix with impact `severe` (full impersonation of any user, or no authentication at all) and ease of attack `easy` (a public user name such as `alice`, a name and password committed to the repository, or nothing at all is enough). Both inputs are recorded in the evidence.
- **Evidence:** `subject` (`requires.auth`), `authKind`, `sourcesRead` (in cds priority order, lowest first), `sourcesNotRead` (the fixed list `.cdsrc-private.json`, `.cdsrc.js`, `.env`, `CDS_* environment variables`), `impact`, `easeOfAttack`.
- **Location:** the source read that cds applies last (`package.json`, else `.cdsrc.json`, else `.cdsrc.yaml`), without a line. No location when none of the three files could be read.
- **Remediation:** Configure a production authentication strategy, for example in `package.json`: `"cds": { "requires": { "[production]": { "auth": "xsuaa" } } }` (or `"ias"`), bind the app to an XSUAA or IAS instance, and keep `mocked` and its users under `[development]` only. Verify the result with `cds env get requires.auth --profile production`.
- **References:** <https://cap.cloud.sap/docs/node.js/authentication>, <https://cap.cloud.sap/docs/node.js/cds-env>, <https://owasp.org/Top10/2025/A07_2025-Authentication_Failures/>
- **Limits / what does not trigger:**
  - `authKind` null (nothing configured) produces no finding: CAP defaults to `jwt` in production. `jwt`, `xsuaa`, `ias`, `ams` and unknown strategies (`other`) produce no finding either.
  - A `mocked` configuration that applies only to the `development` profile does not trigger; mocked users and their passwords are the subject of `CAP_MOCKED_USER_PASSWORD`, and `restrict_all_services` on its own is not a finding.
  - cds reads more sources than the collector opens, because they hold credentials: `.cdsrc.js` (same tier as `.cdsrc.yaml`/`.cdsrc.json`, below `package.json#cds`), and above `package.json#cds` the files `.cdsrc-private.json`, `default-env.json` (deprecated), `.env`, `.<profile>.env` (for example `.production.env`) and the `CDS_CONFIG` and `CDS_*` environment variables. Any of them can still override the strategy at runtime, in either direction, so the finding reflects the committed configuration only and names the main ones in `sourcesNotRead`.
  - The older spellings `mocked-auth`, `basic-auth` and `dummy-auth` are normalised to the current names by the collector and trigger as well.
  - The location names the highest-priority file that was read, not necessarily the one that sets `requires.auth`; the collector does not record which source won the merge.
  - The CAP documentation pages were verified from the `cap-js/docs` GitHub mirror (`node.js/authentication.md`, `node.js/cds-env.md`) because `cap.cloud.sap` does not resolve from the build environment; the links are the canonical pages those files publish to. That page documents `basic` only as the `mocked` strategy without the predefined mock users (the project's own `users` still apply), which is why the rule treats it the same way. The source tiers above are the "Sources for cds.env" table of `cds-env.md`, which also documents `--profile` as a bootstrap argument of the cds CLI (used by the remediation's `cds env get … --profile production`). The OWASP link follows the `A07_2025-Authentication_Failures` entry in the OWASP/Top10 `2025/mkdocs.yml`.

## CAP_MOCKED_USER_PASSWORD

**Mocked users are defined with a password in a project configuration file.** The `mocked` and `basic` authentication strategies take their users from `cds.requires.auth.users`, where each user may carry a `password`. A password in `package.json` or `.cdsrc.json` travels with every clone, every fork and every CI log, and people reuse passwords, so it is worth more to an attacker than the local login it protects.

- **Data:** `cds.effective.<view>.mockedUsersWithPassword` and `mockedUsers` for the `development` and `production` views, computed by the project collector from `.cdsrc.yaml`, `.cdsrc.json` and `package.json#cds` merged in cds order with `[development]`/`[production]` (and `[…!]`) blocks applied at every nesting level. The collector counts the keys of `requires.auth.users` and how many of them have a `password` key; it never reads the user names, the passwords, roles or attributes. `sourcesRead` records which of the three files were read and parsed and carried a cds configuration (`package.json` only when it has a `cds` key); a file that exists but is unreadable or malformed is listed under `unreadable` instead and does not appear.
- **Trigger:** `mockedUsersWithPassword > 0` in the development or the production view. One finding per project; the subject is the configuration key `requires.auth.users`. When both views carry passwords, the finding reports the production view (the one reachable from the deployed app).
- **Severity:** from the criticality matrix, ease of attack `complex` in both cases (the attacker needs read access to the repository or a build artifact first).
  - `medium` = (`moderate`, `complex`): the **production** view has users with passwords and `CAP_MOCKED_AUTH_IN_PROD` does not fire (production auth is unset, `jwt`, `xsuaa`, `ias`, `ams` or another real strategy). The users are dead configuration in production, but the passwords are published.
  - `low` = (`minor`, `complex`): otherwise. Either the passwords exist only in the **development** view, where they protect nothing beyond a local login, or production auth is `mocked`, `dummy` or `basic`, in which case `CAP_MOCKED_AUTH_IN_PROD` already reports the impersonation risk as `critical` and this finding only adds the password hygiene point.
- **Evidence:** `subject` (`requires.auth.users`), `view` (`development` or `production`), `usersWithPassword` (count), `mockedUsers` (count), `authKind` (the view's strategy, or null), `impact`, `easeOfAttack`. The title names the view.
- **Location:** the source read that cds applies last (`package.json`, else `.cdsrc.json`, else `.cdsrc.yaml`), without a line. No location when none of the three files could be read.
- **Remediation:** Delete the `password` values from the mocked users in `cds.requires.auth.users` and keep the `users` block under `[development]` only, so it never applies to production. A developer who needs a password-protected local login can define it in `.cdsrc-private.json`, which cds reads but which must stay out of version control. If any of these passwords was ever reused on another system, change it there.
- **References:** <https://cap.cloud.sap/docs/node.js/authentication#mocked>, <https://cap.cloud.sap/docs/node.js/cds-env>, <https://owasp.org/Top10/2025/A07_2025-Authentication_Failures/>
- **Limits / what does not trigger:**
  - Mocked users without a `password` key do not trigger, whatever their number, and neither does a project with no `users` block. A `mocked`, `dummy` or `basic` production strategy on its own is the subject of `CAP_MOCKED_AUTH_IN_PROD`, not of this rule.
  - The pre-defined users that `@sap/cds` ships (`alice`, `bob`, …) are built-in defaults, not project configuration, and are not counted.
  - `.cdsrc-private.json`, `.cdsrc.js`, `.env`, `default-env.json`, `CDS_CONFIG` and `CDS_*` environment variables rank above the files read and are never opened (they hold credentials), so passwords defined only there are not seen and the finding reflects the committed configuration only.
  - The rule does not know whether a password is weak, strong, or a placeholder: any `password` key counts. It also does not check `.gitignore`: a `package.json` is always treated as committed.
  - The location names the highest-priority file that was read, not necessarily the one that defines the users; the collector does not record which source won the merge.
  - The CAP documentation pages were verified from the `cap-js/docs` GitHub mirror (`node.js/authentication.md`, heading "Mocked Authentication" with anchor `mocked`, and `node.js/cds-env.md`) because `cap.cloud.sap` does not resolve from the build environment; the links are the canonical pages those files publish to. The OWASP link follows the `A07_2025-Authentication_Failures` entry in the OWASP/Top10 `2025/mkdocs.yml`.

## CAP_AUDITLOG_MISSING

**Personal data is modelled but audit logging is not set up.** The CDS model holds personal data, declared with `@PersonalData` or recognisable from field names, but the project neither depends on the `@cap-js/audit-logging` plugin at runtime nor configures `cds.requires.audit-log` for production. CAP logs reads of sensitive data and changes of personal data only through that plugin (or a configured `audit-log` service), so without it nobody can tell afterwards who accessed which person's data, which data-protection regulations require and incident response depends on.

- **Data:** `packageJson.dependencies` and `devDependencies` (package names only), `cds.effective.production.auditLogConfigured` (whether `requires.audit-log` is present and not `false` in any shape, computed by the project collector from `.cdsrc.yaml`, `.cdsrc.json` and `package.json#cds` merged in cds order with `[production]` and `[production!]` blocks applied), and the CDS facts the collector keeps per `*.cds` file: entity names, element names, associations, and whether `@PersonalData` appears on an entity, one of its elements, or in an `annotate` statement. The rule reads them through the shared model helpers (`hasPersonalDataDeclared`, `effectiveEntities`, `personalEntities`), which resolve `using … as` aliases and namespace-qualified names.
- **Trigger:** `@sap/cds` is listed under `dependencies`, **and** the model holds personal data (`@PersonalData` is declared anywhere, or at least one entity is inferred to be personal: a strong field such as `email`, `phone`, `firstName`, `birthDate`, `iban`, `salary`, or weak address fields on an entity that links to a personal entity or is named like one), **and** neither `@cap-js/audit-logging` is listed under `dependencies` nor `requires.audit-log` is configured for production. One finding per project; the subject is the configuration key `requires.audit-log`.
- **Severity:** from the criticality matrix (the attacker needs an account or a foothold first; what the missing log costs is the ability to detect and reconstruct the access afterwards).
  - `high` = (`significant`, `advanced`): `@PersonalData` is declared, so the project knows it processes personal data and the plugin would log it generically as soon as it is added.
  - `medium` = (`moderate`, `advanced`): personal data is only inferred from field names; the annotations are missing as well (`CAP_PERSONAL_DATA_UNANNOTATED` reports those per entity).
  - The same two cells apply, with the title "Audit logging plugin is listed under devDependencies only, so it is inactive in production", when `@cap-js/audit-logging` appears under `devDependencies` but not under `dependencies`: `@sap/cds` fetches plugins from `devDependencies` only while `NODE_ENV` is not `production` (`lib/plugins.js`, `fetch(DEV = process.env.NODE_ENV !== 'production')`), and cds-dk's own `cds add audit-logging` test (`hasInProduction`) reads `dependencies` only, so the deployed app runs without the plugin.
  - `low` = (`minor`, `complex`), with the title "Audit logging uses the legacy client library; personal-data access is not logged automatically": `@sap/audit-logging` is listed under `dependencies` instead of the plugin. The project chose audit logging, but the legacy library offers a programmatic API only, so only the events the code logs explicitly are recorded; an attacker who wants to stay unnoticed first has to learn which paths the code logs, hence `complex`. This branch applies whether the personal data is declared or inferred, and takes precedence over a dev-only plugin.
- **Evidence:** `subject` (`requires.audit-log`), `personalDataDeclared` (boolean), `declaredEntities` (count of entities marked `@PersonalData` after merging `annotate` statements), `inferredEntities` (count of entities that look personal and carry no `@PersonalData`), `legacyLibrary` (boolean), `pluginInDevDependencies` (boolean), `impact`, `easeOfAttack`. Entity and field names are not repeated here; `CAP_PERSONAL_DATA_UNANNOTATED` names the inferred entities.
- **Location:** `package.json`, without a line: `cds add audit-logging` records the plugin there, so that is where the fix lands.
- **Remediation:** Add the `@cap-js/audit-logging` plugin with `cds add audit-logging`: it configures `cds.requires.audit-log` with console output in development and the SAP Audit Log service (`audit-log-to-restv2`) in production and, when the project has an `mta.yaml`, adds an `auditlog` resource (`org.cloudfoundry.managed-service`, service `auditlog`, plan `premium`) to it. Create an SAP Audit Log service instance (service `auditlog`, plan `premium`) in the target space and bind it to the app. The plugin logs only entities annotated with `@PersonalData`, so when the personal data is only inferred, annotate the personal entities first (`EntitySemantics` and `DataSubjectRole` on the entity; `FieldSemantics`, `IsPotentiallyPersonal` or `IsPotentiallySensitive` on the elements) and keep the annotations complete. When the plugin sits under `devDependencies`, move it to `dependencies`. With the legacy library, replace `@sap/audit-logging` by the plugin and keep the `auditlog` binding. Verify with `cds env requires.audit-log --profile production`.
- **References:** <https://cap.cloud.sap/docs/guides/security/dpp-audit-logging>, <https://cap.cloud.sap/docs/guides/security/dpp-annotations>, <https://owasp.org/Top10/2025/A09_2025-Security_Logging_and_Alerting_Failures/>
- **Limits / what does not trigger:**
  - Projects without `@sap/cds` under `dependencies` are not Node.js CAP apps and produce no finding (`cds init` puts `@sap/cds` there; CAP Java projects configure audit logging in `pom.xml`, which is not read, and get `requires.audit-log: true` in `.cdsrc.json` from `cds add audit-logging`, which the collector does see). A project that lists `@sap/cds` under `devDependencies` only is treated as a tooling or Java project and skipped.
  - A model without personal data, declared or inferred, produces no finding, whatever the dependencies. Entities with weak fields only (`city`, `postCode`, `country`, …) that neither link to a personal entity nor are named like one (`Warehouses`) do not count. The inference uses the field-name lists in `analyzers/project/patterns.ts`; a personal entity whose fields are named differently (`col1`, abbreviations, non-English names) is not recognised.
  - `@cap-js/audit-logging` under `dependencies`, or `requires.audit-log` configured for the production profile in any shape (`true`, a kind string, or an object; an explicit `false` does not count), suppresses the finding. The rule does not verify that the configured kind actually reaches the SAP Audit Log service, that the `handle` option still covers `READ` and `WRITE`, or that an `auditlog` instance is bound: `CAP_AUDITLOG_NOT_BOUND` checks the binding. A configuration under `[development]` only does not count. `@sap/audit-logging` under `devDependencies` only is ignored for the same reason the plugin is: it is not installed in production.
  - `.cdsrc-private.json`, `.cdsrc.js`, `.env`, `default-env.json`, `CDS_CONFIG` and `CDS_*` environment variables rank above the files read and are never opened (they hold credentials), so an `audit-log` configuration placed only there is not seen and the finding reflects the committed configuration only. The `CDS_PLUGINS` environment variable, which can register plugins outside `package.json`, is not seen either.
  - The CAP documentation pages were verified from the `cap-js/docs` GitHub mirror (`guides/security/dpp-audit-logging.md`, which documents the `audit-log-to-console`/`audit-log-to-restv2` presets, the `vcap.label: auditlog` binding, the `cds env requires.audit-log --profile production` command and the `auditlog` service with plan `premium`; and `guides/security/dpp-annotations.md`; both are listed under `guides/security/_menu.md` and `.vitepress/rewrites.js` does not rename them) because `cap.cloud.sap` does not resolve from the build environment; the links are the canonical pages those files publish to. The former `guides/data-privacy/*` paths no longer exist in the mirror. What `cds add audit-logging` writes was read from the `@sap/cds-dk` package (`lib/init/template/audit-logging`: `@cap-js/audit-logging` under `dependencies` for Node.js, `requires.audit-log: true` for Java, and the `mta.yaml` resource with `service-plan` defaulting to `premium`). That `@sap/audit-logging` is the legacy client library is taken from the design review facts and the npm registry (`@sap/audit-logging`: "Provides audit logging functionalities for Node.js applications", no CDS integration); the SAP Help page on the Audit Log Write API that the CAP guide links to could not be verified and is therefore not listed. The OWASP link follows the `A09_2025-Security_Logging_and_Alerting_Failures` entry in the OWASP/Top10 `2025/mkdocs.yml`.

## CAP_AUDITLOG_NOT_BOUND

**Audit logging is installed but no audit log service is bound.** The project depends on the `@cap-js/audit-logging` plugin and its production kind writes to a service binding (`audit-log-to-restv2` finds the SAP Audit Log service by the VCAP label `auditlog`, `audit-log-to-alsng` by the binding name `auditlog-ng`), but the MTA descriptor declares no such instance. This is the state a Node.js project is in right after `cds add audit-logging`, which adds the dependency and the `auditlog` resource but no `cds.requires.audit-log` entry, when the resource is later removed or the descriptor was written by hand. Without a binding the plugin's production service throws `No or malformed credentials for "audit-log"` on the first `cds.connect.to('audit-log')`, which its read and modification handlers await without catching, so the first access to personal data in production fails or, where the error is swallowed higher up, leaves no audit entry, even though the project looks as if it logs them.

- **Data:** `packageJson.dependencies` and `devDependencies` (package names only), `cds.effective.production.auditLogKind` and `auditLogConfigured` (computed by the project collector from `.cdsrc.yaml`, `.cdsrc.json` and `package.json#cds` merged in cds order with `[production]` and `[production!]` blocks applied), and the facts the collector keeps from `mta.yaml` / `mta.yml`: resource `name`, `type`, `parameters.service`, and the `requires` names of every module. No other part of the descriptor is read.
- **Trigger:** `@cap-js/audit-logging` is a dependency, **and** an MTA descriptor exists, **and** the production `audit-log` kind is `audit-log-to-restv2`, `audit-log-to-alsng` or unset (the plugin's own defaults then select `audit-log-to-restv2` for production), **and** the descriptor binds no audit log instance: no resource has `service: auditlog`, no resource of type `org.cloudfoundry.existing-service` or `org.cloudfoundry.user-provided-service` has a name containing `audit`, and no module requires a resource named `auditlog-ng`. One finding per project; the subject is the CF service name `auditlog`.
- **Severity:** `medium` = (`moderate`, `advanced`) from the criticality matrix: an attacker still needs an account or a foothold to touch personal data (`advanced`), and what the missing binding costs is the ability to detect and reconstruct that access afterwards, which `CAP_AUDITLOG_MISSING` rates the same for a project that never set audit logging up (`moderate`). The project here chose audit logging, so the fix is a descriptor change, not a design change.
- **Evidence:** `subject` (`auditlog`), `auditLogKind` (the production kind, or `null`), `auditLogConfigured` (boolean), `modules` and `resources` (counts of entries in the descriptor), `impact`, `easeOfAttack`. Resource, module and service names from the descriptor are not repeated.
- **Location:** `mta.yaml` or `mta.yml` (whichever exists), without a line: the collector keeps no positions from the descriptor.
- **Remediation:** Add an SAP Audit Log service instance to the MTA descriptor and require it from the server module: a resource of type `org.cloudfoundry.managed-service` with `service: auditlog` and `service-plan: premium` (what `cds add audit-logging` generates), or `org.cloudfoundry.existing-service` named after an instance created with `cf create-service auditlog premium <name>`; then list the resource under the module `requires`. The plugin finds the `audit-log-to-restv2` binding by its VCAP label `auditlog`; with Audit Log Service NG (`audit-log-to-alsng`) the binding must be named `auditlog-ng`. Without a binding the audit log service cannot initialise in production and audit entries are not written. Verify with `cds env requires.audit-log --profile production` and `cf services`.
- **References:** <https://cap.cloud.sap/docs/guides/security/dpp-audit-logging>, <https://github.com/cap-js/audit-logging>, <https://help.sap.com/docs/btp/sap-business-technology-platform/audit-log-write-api-for-customers>, <https://owasp.org/Top10/2025/A09_2025-Security_Logging_and_Alerting_Failures/>
- **Limits / what does not trigger:**
  - Projects without `@cap-js/audit-logging` in `dependencies` or `devDependencies` produce no finding, whatever the descriptor says: a project that uses the legacy `@sap/audit-logging` library, or none at all, is `CAP_AUDITLOG_MISSING`'s business. A plugin listed only in `devDependencies` still counts here, because the question is whether the project adopted the plugin, and the binding is missing either way; that the plugin is then inactive in the deployed app is reported by `CAP_AUDITLOG_MISSING` ("listed under devDependencies only"), so such a project gets both findings.
  - Projects without `mta.yaml` / `mta.yml` produce no finding: `manifest.yml`, Kyma/Helm charts and `cf bind-service` done by hand are not read, so a binding created that way is invisible and the rule cannot say anything about it. For the same reason a descriptor that binds an existing instance under a name without `audit` in it (`org.cloudfoundry.existing-service` named `my-logs`) is reported as unbound: the descriptor does not carry the instance's service name, so the resource name is the only clue, and the finding then asks for a recognisable name or a `service: auditlog` managed resource.
  - A production kind of `audit-log-to-console`, `audit-log-to-library` or any other string (`audit-log-to-als`, a custom kind) produces no finding: those kinds need no binding, or the rule cannot tell what they need. A configuration without a `kind` (`audit-log: true`, or an object that only sets `impl`, `handle` or `outbox`) keeps the plugin's production default and fires; a custom `impl` that needs no binding is therefore reported, since the collector keeps no `impl` fact. `audit-log: false` in production, which disables the service, is indistinguishable from an absent configuration (both are `auditLogConfigured: false` with no kind) and fires as well. Only the production view counts; a `[development]` block with `audit-log-to-console` changes nothing, and a production kind under `[production]` is taken as written.
  - A resource with `service: auditlog` of any type, a resource of type `org.cloudfoundry.existing-service` or `org.cloudfoundry.user-provided-service` whose name contains `audit` (case-insensitive), or a module requiring a resource named exactly `auditlog-ng` suppresses the finding. A `managed-service` resource that merely has `audit` in its name but a different `service`, and a module requiring a resource whose name only contains `auditlog-ng`, do not. The rule does not check that the server module actually lists the audit log resource in its `requires`, that the plan is `premium`, or that the instance exists in the target space.
  - `.cdsrc-private.json`, `.cdsrc.js`, `.env`, `default-env.json`, `CDS_CONFIG` and `CDS_*` environment variables, and `*.mtaext` extension descriptors are never read (they hold credentials), so a kind or a resource added only there is not seen.
  - The plugin's binding resolution was verified from the `cap-js/audit-logging` repository on GitHub (`package.json`: `audit-log-to-restv2` with `vcap.label: auditlog`, `audit-log-to-alsng` with `vcap.name: auditlog-ng`, `[production]` and `[hybrid]` defaulting to `audit-log-to-restv2`, `[development]` to `audit-log-to-console`; `srv/log2restv2.js`: the credentials check quoted above; `lib/access.js` and `lib/modification.js`: the lazy `cds.connect.to("audit-log")` with no error handling), the service name and plan from the SAP Help page "Audit Log Write API for Customers" through the `SAP-docs/btp-cloud-platform` GitHub mirror (`cf create-service auditlog premium <my-service-instance>`, `cf bind-service`), and the `org.cloudfoundry.existing-service` resource example (`my-auditlog-service`) from the CAP guide through the `cap-js/docs` mirror (`guides/security/dpp-audit-logging.md`, which installs the plugin with `npm add @cap-js/audit-logging`). What `cds add audit-logging` writes was verified from the `@sap/cds-dk` 10.2.0 package on the npm registry (`lib/init/template/audit-logging`): for Node.js only the `@cap-js/audit-logging` dependency (no `cds.requires.audit-log`), and in `mta.yaml` a resource `<app>-auditlog` of type `org.cloudfoundry.managed-service` with `service: auditlog` and `service-plan: premium` unless `--plan` says otherwise, inserted into the srv module's `requires`. `cap.cloud.sap` and `help.sap.com` do not resolve from the build environment, so the links are the canonical pages those sources publish to; the SAP Help link is the one both the plugin's README and the CAP guide give. The OWASP link follows the `A09_2025-Security_Logging_and_Alerting_Failures` entry in the OWASP/Top10 `2025/mkdocs.yml`.

## CAP_PERSONAL_DATA_UNANNOTATED

**Entity holds personal data without @PersonalData annotations.** An entity has elements that look like personal data (names, contact details, identifiers such as a tax id or an IBAN, or address parts on an entity that belongs to a person), but neither the entity nor an `annotate` statement carries `@PersonalData`. CAP derives its data-privacy handling from these annotations: the `@cap-js/audit-logging` plugin logs reads of sensitive and changes of personal data only for annotated entities, and the data-retention and personal-data-manager integrations find data subjects through them. Without the annotations the data is stored and served like any other, so access to it is neither logged nor governed.

- **Data:** the CDS facts the project collector keeps per `*.cds` file: top-level and namespaced entity names, their element names, their associations and compositions (`{ field, target }`), `using … as` aliases, whether `@PersonalData` appears on the entity header or any element, and `annotate` statements with whether `@PersonalData` appears anywhere in them. No element types, values, titles or other annotations are read. The rule reads them through the shared model helper `personalEntities`, which resolves aliases and namespace-qualified names and merges `annotate` statements (an annotate on a service projection counts for the db entity when that projection is `as projection on` it).
- **Trigger:** an entity that is personal by one of three reasons, and not `@PersonalData` after merging annotates. One finding per entity; the subject is the entity name as written.
  - `strong-fields`: at least one element whose name (lowercased, `_`/`-` removed) is in the strong list of `analyzers/project/patterns.ts` (`email`, `phone`, `mobile`, `firstName`, `lastName`, `birthDate`, `ssn`, `taxId`, `iban`, `creditCard*`, `salary`, `gender`, `religion`, …, and `*phone`/`*mail`/`*fax`/`*email` suffixes such as `workEmail`).
  - `linked-entity`: only weak elements (`street*`, `city`, `postCode`, `zipCode`, `latitude`, `longitude`, `country`) and an association or composition to an entity that has a strong element or is `@PersonalData`.
  - `entity-name`: only weak elements and the entity's last name segment matches `address|contact|person|customer|employee|user|patient|member|applicant` (case-insensitive).
- **Severity:** `medium` = (`moderate`, `advanced`) for every branch: an attacker needs an account or a foothold to reach the data, and what the missing annotation costs is the logging, retention and subject-request handling CAP would apply, not the data itself. The three titles name the reason: "Entity holds personal data without @PersonalData annotations", "Entity holds address data of a personal entity without @PersonalData annotations", "Entity whose name suggests personal data holds address data without @PersonalData annotations" (the name pattern also matches `Addresses`, `Contacts` and `UserSettings`, which are not persons, so the title does not say so).
- **Evidence:** `subject` (entity name), `reason` (`strong-fields`, `linked-entity` or `entity-name`), `strongFields` and `weakFields` (the matching element names, in model order), `linkedTo` (the personal entity an association points to when that is the reason, else `null`), `impact`, `easeOfAttack`. Only identifiers are copied: no element types, defaults, titles or doc comments.
- **Location:** the `.cds` file and the line of the `entity` definition.
- **Remediation:** Annotate the entity, preferably in a separate `db/data-privacy.cds` file: `annotate <Entity> with @PersonalData: { EntitySemantics: 'DataSubject', DataSubjectRole: '<Role>' }` for the entity that represents the person, or `EntitySemantics: 'DataSubjectDetails'` for an entity that belongs to one through an association; mark the key, or the association to the data subject, with `@PersonalData.FieldSemantics: 'DataSubjectID'`, each personal element with `@PersonalData.IsPotentiallyPersonal` and sensitive ones (salary, religion, card numbers) with `@PersonalData.IsPotentiallySensitive`. With the `@cap-js/audit-logging` plugin in place (`cds add audit-logging`; `CAP_AUDITLOG_MISSING` reports when it is not), changes of personal and reads of sensitive elements are then logged. The finding is inferred from element and entity names: if the elements are not personal data (a warehouse address, a company's contact mailbox), rename them so they no longer look like it, or accept the finding.
- **References:** <https://cap.cloud.sap/docs/guides/security/dpp-annotations>, <https://cap.cloud.sap/docs/guides/security/dpp-audit-logging>, <https://owasp.org/Top10/2025/A04_2025-Cryptographic_Failures/>, <https://owasp.org/Top10/2025/A09_2025-Security_Logging_and_Alerting_Failures/>
- **Limits / what does not trigger:**
  - Entities with weak elements only that neither link to a personal entity nor are named like one (`Warehouses` with `city` and `postCode`, `Plants` with coordinates) produce no finding, nor do entities without any personal-looking element (`Incidents` with `title` and `status`), even when they link to a customer. An association to an entity that is itself not personal does not count.
  - `@PersonalData` declared inline on the entity or one of its elements, through an `annotate` on the entity (by exact name, `using` alias or namespace-qualified suffix), or through an `annotate` on a service projection whose `as projection on` resolves to the entity, suppresses the finding. An annotate on a service entity that is not a recognisable projection (no `projectionOf`) does not reach the db entity, so the finding stays. The rule checks only that `@PersonalData` is present somewhere on the entity, not that `EntitySemantics`, `DataSubjectID` or the element-level flags are complete, and it does not check whether the audit-logging plugin is installed (`CAP_AUDITLOG_MISSING` does).
  - The inference uses the English field-name lists in `analyzers/project/patterns.ts`: a personal entity whose elements are named differently (`col1`, abbreviations, non-English names) is not recognised, and a non-personal element that happens to match (`country` of a plant, `mail` as a postal batch) may be reported; the `entity-name` branch matches on the name alone, so a non-personal entity such as `UserSettings` or `CustomerSites` that is named like one and has an address element is reported too, while `Regions` or `Depots` with the same elements are not. An association from a weak-field entity counts only when its target has a strong element or `@PersonalData`: a target that is personal by its name alone (`Contacts` with `city` only) does not make the linking entity personal, and a self-association never does. Entities defined inside a service block (`service S { entity X { … } }`) are collected as service entities, not db entities, and are not checked here.
  - Two files that define an entity with the same written name (for example the same `entity Customers` under two namespaces) yield one finding, located at the first file in path order; the collector stores names as written, so the rule cannot tell them apart.
  - The CAP documentation pages were verified from the `cap-js/docs` GitHub mirror (`guides/security/dpp-annotations.md`, which documents `EntitySemantics` with the values `DataSubject`, `DataSubjectDetails` and `Other`, `DataSubjectRole`, `FieldSemantics: 'DataSubjectID'`, `IsPotentiallyPersonal`, `IsPotentiallySensitive` and the separate `data-privacy.cds` file; and `guides/security/dpp-audit-logging.md`, which documents the `PersonalDataModified` and `SensitiveDataRead` events the plugin emits) because `cap.cloud.sap` does not resolve from the build environment; the links are the canonical pages those files publish to. The OWASP links follow the `A04_2025-Cryptographic_Failures` and `A09_2025-Security_Logging_and_Alerting_Failures` entries in the OWASP/Top10 `2025/mkdocs.yml`.

## CAP_SERVICE_NO_RESTRICTION

**A served CDS service has no access control at all.** Neither the service nor any of its entities or actions carries `@requires` or `@restrict`, in the definition or in an `annotate` statement. CAP adds an implicit `@requires: 'authenticated-user'` to such services in production, so every user who can log in can read, and unless an entity is `@readonly`, change its data. When the production profile sets `restrict_all_services: false` or a development authentication strategy, that implicit requirement is gone and the service answers anonymous requests too.

- **Data:** the effective services of the project (`effectiveServices` in `analyzers/project/cdsModel.ts`): every `service` found in `*.cds` files with its entities and actions, merged with `@requires`/`@restrict.to` from `annotate` statements that target the service, `Service.Entity` or `Service.action` (by exact name, `using … as` alias or namespace-qualified suffix), plus `@protocol: 'none'` and `@cds.external` markers; for each service entity the database entity it projects on (`projectionOf`, alias-resolved) and the `annotate` statements that restrict it; `cds.effective.production.restrictAllServices` and `cds.effective.production.authKind` from the merged cds configuration.
- **Trigger:** a service whose merged `requires` and `restrictTo` are both empty, none of whose projected database entities is restricted by an `annotate` statement (CAP propagates such a restriction to the projection), that is not `@protocol: 'none'`, not `@cds.external`, and whose file is not under `srv/external/`. One finding per service name per project (the first declaration in file order when a name appears twice); the subject is the service name.
- **Severity:** from the criticality matrix, both inputs recorded in the evidence.
  - `critical` (impact `severe`, ease of attack `easy`) with the title "Service is open to everyone" when the production profile sets `restrict_all_services: false` or its authentication strategy is `mocked`, `dummy` or `basic`: nobody has to log in.
  - `high` (impact `significant`, ease of attack `advanced`) when at least one entity is not `@readonly` or the service has an action or function: any authenticated user can change data or trigger logic, but needs an account first. (The design review table paired this branch with ease `easy`, which the matrix maps to `critical`; the named severity `high` was kept and the ease input adjusted to match it.)
  - `medium` (impact `moderate`, ease of attack `advanced`) when every entity is `@readonly` and there are no actions, including a service with no entities: any authenticated user can read everything, but not change it.
- **Evidence:** `subject` (service name), `restrictAllServices` (production value, `null` when unset), `authKind` (production value, `null` when unset), `entities`, `writableEntities` and `actions` (counts), `impact`, `easeOfAttack`.
- **Location:** the `.cds` file and the line of the `service` keyword.
- **Remediation:** Restrict the service with `@requires`, for example `service AdminService @(requires: 'admin') { ... }`, using a role that `xs-security.json` defines as a scope and role template, and add `@restrict` rules on entities or actions that need finer control (`@restrict: [{ grant: 'READ', to: 'viewer' }]`). Mark data that must never be changed through the service with `@readonly`. A service that is only consumed in-process should declare `@protocol: 'none'`. If the service must stay open to every authenticated user, say so explicitly with `@requires: 'authenticated-user'`. When the production profile sets `restrict_all_services: false` or a development authentication strategy, remove that as well, since it lets unauthenticated callers in.
- **References:** <https://cap.cloud.sap/docs/guides/security/authorization>, <https://cap.cloud.sap/docs/node.js/authentication>, <https://owasp.org/Top10/2025/A01_2025-Broken_Access_Control/>
- **Limits / what does not trigger:**
  - Any explicit restriction counts, including a pseudo-role: `@requires: 'authenticated-user'` or `@requires: 'any'` is a documented decision, not a missing one, and produces no finding. Whether the roles used exist in XSUAA is the subject of `CAP_ROLE_NOT_IN_XSUAA`.
  - A restriction on a single entity or action silences the rule for the whole service, because the author has evidently thought about access control there; the rule does not report the remaining unrestricted members.
  - Internal services (`@protocol: 'none'`), imported remote services (`@cds.external`) and anything under a `srv/external/` directory are skipped. A file whose name merely contains `external` (for example `srv/externalCatalog.cds`) is not.
  - `restrict_all_services` and the authentication strategy come from `.cdsrc.yaml`, `.cdsrc.json` and `package.json#cds` only; `.cdsrc-private.json`, `.cdsrc.js`, `.env` and `CDS_*` environment variables are never read and can change the result at runtime (see `CAP_MOCKED_AUTH_IN_PROD`). The development profile is ignored.
  - Annotations are matched by name. An `annotate` that reaches the service only through an `extend`, a model imported from `node_modules`, or a build-time plugin is not seen, so such a service is reported although it is restricted at runtime. Services generated by CAP itself (for example `cds.xt.*` MTX services) are not in the project's `.cds` files and are never reported.
  - A restriction written inline on the database entity (`entity Books @(restrict: […]) { … }` in `db/`) is inherited by every projection at runtime, but the collector records `@requires`/`@restrict` on services, their members and `annotate` statements only, so a service whose only restriction is inherited that way is still reported. The same restriction expressed as `annotate db.Books with @restrict: […];` is seen.
  - An `@restrict` rule without a `to` property (which cds reads as `to: 'any'`), or with only `grant` and `where`, is not recorded because the collector keeps role names only; a service whose only access rule has that shape is reported as unrestricted.
  - `@readonly` is detected on the service entity only; a projection that is read-only because its source is a view, or because of `@insertonly`/`@Capabilities` annotations, still counts as writable.
  - The CAP pages were verified from the `cap-js/docs` GitHub mirror (`guides/security/authorization.md`, which states that by default CDS services have no access control and that authenticated users then have access to all entities, that service entities inherit the restriction of the database entity they project on ("Propagation of Restrictions"), and that `any` is the default when a privilege has no `to`; and `node.js/authentication.md`, which documents `restrict_all_services`) because `cap.cloud.sap` does not resolve from the build environment; the links are the canonical pages those files publish to. The OWASP link follows the `A01_2025-Broken_Access_Control` entry in the OWASP/Top10 `2025/mkdocs.yml`.

## CAP_ROLE_NOT_IN_XSUAA

**A role the CDS model requires does not exist as an XSUAA scope.** `@requires: 'auditor'` or `@restrict: [{ to: 'auditor' }]` only ever lets a user in when the XSUAA token carries the scope `$XSAPPNAME.auditor`, and that scope exists only when the security descriptor (`xs-security.json`, or the `config` of the xsuaa resource in `mta.yaml`) declares it. CAP generates one scope and one role template per CDS role with exactly that name; when the descriptor is written or edited by hand, or the model moves on after it was generated, a role can be required that nobody can be granted. The restriction then either locks every user out of that service, entity or action, or, when the name is a typo of a role that does exist, the intended rule is not the one that applies.

- **Data:** the roles named in `@requires` and `@restrict.to` on services, their entities and actions, and in `annotate` statements, read through `referencedRoles` in `analyzers/project/cdsModel.ts` (pseudo-roles and names containing `$` or `:` are dropped there); the scope names of every XSUAA descriptor the collector found (`xsSecurity[].scopes[].name`, from `xs-security.json` files and from `parameters.config.scopes` of xsuaa resources in `mta.yaml`); `packageJson.dependencies` and `devDependencies` (package names only); `cds.effective.production.authKind` from the merged cds configuration.
- **Trigger:** at least one descriptor declares a scope or a role template, and a referenced role has no scope named `$XSAPPNAME.<role>` or `<role>` in any descriptor. The comparison is exact (case-sensitive, no normalisation). One finding per role per project; the subject is the role name.
- **Severity:** from the criticality matrix, both inputs recorded in the evidence.
  - `medium` (impact `moderate`, ease of attack `advanced`) always: the worst case is a restriction that silently differs from the modelled one, but an attacker still needs an account and a role assignment to benefit from it.
- **Evidence:** `subject` and `role` (the role name), `descriptors` (every descriptor file of the project, sorted by code point), `scopesChecked` (number of distinct scope names across them), `impact`, `easeOfAttack`.
- **Location:** the `.cds` file and line where the role is first named: the first file in the collector's order (paths sorted by code point, so `srv/B.cds` precedes `srv/a.cds`), then the lowest line among the service, its entities, its actions and the `annotate` statements in that file. That is where a typo gets fixed; the scope itself is added to the descriptor.
- **Remediation:** Add a scope `$XSAPPNAME.<role>` and a role template `<role>` with that scope in its `scope-references` to xs-security.json (or regenerate the file from the model with `cds compile srv --to xsuaa > xs-security.json`), update the xsuaa service instance and assign the role through a role collection. If the name in `@requires` or `@restrict` is a typo, fix the annotation so that it matches an existing scope. When roles are meant to come from Authorization Management Service policies, add `@sap/ams` and configure `cds.requires.auth: ams` for production.
- **References:** <https://cap.cloud.sap/docs/guides/security/cap-users#xsuaa-roles>, <https://cap.cloud.sap/docs/guides/security/authorization>, <https://help.sap.com/docs/btp/sap-business-technology-platform/application-security-descriptor-configuration-syntax>, <https://owasp.org/Top10/2025/A01_2025-Broken_Access_Control/>, <https://owasp.org/Top10/2025/A07_2025-Authentication_Failures/>
- **Limits / what does not trigger:**
  - A project without any descriptor produces no finding: there is nothing to compare against, and the roles may be assigned by another component (for example a separately deployed xsuaa instance). Whether a project needs a descriptor at all is not this rule's question.
  - A descriptor that declares neither scopes nor role templates counts as absent for the same reason. `cds add xsuaa` writes `config: { xsappname, tenant-mode }` into the xsuaa resource of `mta.yaml` next to `path: ./xs-security.json`; when that file is generated at build time, ignored by git, larger than 2 MiB or under a skipped directory, the inline block is the only descriptor the collector sees, and comparing roles against it would report every one of them. A descriptor with role templates but no scopes still counts, and its roles are reported.
  - Projects that take their roles from Authorization Management Service policies produce no finding: when `@sap/ams` is a dependency (regular or dev) or the production profile sets `cds.requires.auth: ams`, CAP roles are not XSUAA scopes. The development profile is ignored.
  - Production authentication `ias` without `@sap/ams` is not exempted, because the `ias` strategy also accepts XSUAA tokens during a migration (CAP, "IAS-based Authentication"). Note, though, that IAS tokens carry no scopes at all, so for a pure IAS setup the fix is AMS policies, not a scope in the descriptor.
  - Roles named on `@cds.external` or `@protocol: 'none'` services and on their members are checked like any other: they are roles of this application's model, not of the remote system.
  - Pseudo-roles (`any`, `authenticated-user`, `identified-user`, `registered-user`, `internal-user`, `system-user`, `privileged-user`) are never scopes and are skipped. Roles written with `$` or `:` (`$XSAPPNAME.auditor`, `$REQUEST.x`, `xs:…`) are skipped too, so a role spelt with its XSUAA prefix in the model is neither checked nor reported.
  - A scope defined in any descriptor counts, including one that is also granted to other applications (`granted-apps`, `grant-as-authority-to-apps`), and one read from `mta.yaml`. Role templates are not consulted: a scope without a role template is reported by `XSUAA_SCOPE_UNUSED`, not here.
  - Scope names are compared exactly. `$XSAPPNAME.Auditor` does not satisfy `@requires: 'auditor'`, because XSUAA scopes are case-sensitive, so a case mismatch is reported as a missing scope on purpose.
  - `cds.requires.auth` comes from `.cdsrc.yaml`, `.cdsrc.json` and `package.json#cds` only; `.cdsrc-private.json`, `.cdsrc.js`, `.env` and `CDS_*` environment variables are never read, so an AMS setup configured only there is not recognised and its roles are reported.
  - Roles are matched by name as written in the project's own `.cds` files. Roles required by models imported from `node_modules` or added by plugins are not seen; `mtaext` files and descriptors generated at build time (`cds build`) are never read, so a scope that only exists there is reported as missing.
  - The CAP pages were verified from the `cap-js/docs` GitHub mirror (`guides/security/cap-users.md`, heading "Role Assignment with XSUAA" with anchor `xsuaa-roles`, which states that for every role name in the CDS model one scope and one role template are generated with the exact name of the CDS role, warns that hand-edited scope names must exactly match the role names in the model, and documents `cds compile srv --to xsuaa > xs-security.json` and the AMS alternative; and `guides/security/authorization.md` for `@requires` and `@restrict`) because `cap.cloud.sap` does not resolve from the build environment; the links are the canonical pages those files publish to. The SAP Help page "Application Security Descriptor Configuration Syntax" (loio `517895a9612241259d6941dbf9ad81cb`, which states that local scopes must be prefixed with `$XSAPPNAME` and documents `scope-references`, `granted-apps` and `grant-as-authority-to-apps`) was verified from the `SAP-docs/btp-cloud-platform` GitHub mirror for the same reason; the link is the canonical hub URL. The OWASP links follow the `A01_2025-Broken_Access_Control` and `A07_2025-Authentication_Failures` entries in the OWASP/Top10 `2025/mkdocs.yml`.

## XSUAA_SCOPE_UNUSED

**A scope in the XSUAA security descriptor can never reach a role collection.** No role template references it and it is not granted to another application, so no role, and therefore no role collection and no user, can ever carry it. Such a scope is dead configuration: it suggests a permission that does not exist, or it is the trace of a role template that was removed or renamed without the matching scope, and either way it misstates the authorization model that reviewers and auditors read from the descriptor.

- **Data:** every XSUAA descriptor of the project (`xsSecurity`): each `xs-security.json` found by the walk, and the inline `parameters.config` of every `mta.yaml` resource with `service: xsuaa`; from each, the scope names with whether `granted-apps` or `grant-as-authority-to-apps` is set, and the `scope-references` of every role template. Descriptions, `authorities`, `foreign-scope-references`, `oauth2-configuration` and `xsappname` are never read.
- **Trigger:** a scope without `granted-apps`/`grant-as-authority-to-apps` whose name is not in the `scope-references` of any role template in any descriptor of the project. Names are compared exactly and with a leading `$XSAPPNAME.` stripped from both sides, so `$XSAPPNAME.admin` is satisfied by a reference to `$XSAPPNAME.admin` or to `admin`. One finding per scope per project, with `$XSAPPNAME.x` and `x` counted as the same scope (the first descriptor in file order when it appears twice; two xsuaa resources of one `mta.yaml` are ordered by their number of role templates, then scopes, so the result does not depend on resource order); the subject is the scope name as written in that descriptor.
- **Severity:** from the criticality matrix, both inputs recorded in the evidence.
  - `low` (impact `minor`, ease of attack `complex`), always: nobody gains access through an unassignable scope; the harm is a misleading authorization model and configuration drift, which only pays off for an attacker combined with other mistakes.
- **Evidence:** `subject` (scope name), `source` (`xs-security.json` or `mta.yaml`), `roleTemplates` (count in the descriptor that defines the scope), `descriptors` (count of descriptors in the project), `impact`, `easeOfAttack`.
- **Location:** the descriptor file (`xs-security.json` or `mta.yaml`); no line, since the collector keeps names only.
- **Remediation:** Reference the scope from a role template in the security descriptor, for example `"role-templates": [{ "name": "Admin", "scope-references": ["$XSAPPNAME.admin"] }]`, so it can be assigned through a role collection, or remove the scope. If another application is meant to call with it, grant it explicitly with `granted-apps` or `grant-as-authority-to-apps`. In a CAP project, regenerate the descriptor with `cds compile srv --to xsuaa` so scopes and role templates stay in step with the roles used in the CDS model.
- **References:** <https://help.sap.com/docs/btp/sap-business-technology-platform/application-security-descriptor-configuration-syntax>, <https://help.sap.com/docs/btp/sap-business-technology-platform/building-roles-and-role-collections-for-applications>, <https://cap.cloud.sap/docs/guides/security/cap-users>, <https://owasp.org/Top10/2025/A02_2025-Security_Misconfiguration/>
- **Limits / what does not trigger:**
  - A scope listed in `granted-apps` or `grant-as-authority-to-apps` is meant for another application and produces no finding, whatever the role templates say. The rule does not check that the named applications exist.
  - A reference in any descriptor of the project counts, not only the one that defines the scope: XSUAA merges the inline `config` of the mta.yaml resource with `xs-security.json` at deployment (CAP, "Publish Security Descriptor": "Inline configuration in the mta.yaml `config` block and the xs-security.json file are merged"). The design review table said "in the same descriptor"; the project-wide check was chosen to avoid reporting a scope that a template in the other half of the merged descriptor references. The flip side: in a repository with several unrelated `xs-security.json` files, a template in one application silences a same-named scope in another.
  - Projects without any descriptor, descriptors without scopes, and references to foreign scopes such as `uaa.user` produce nothing: the rule looks only at scopes the project defines. Whether the CDS model uses roles that have no scope is the subject of `CAP_ROLE_NOT_IN_XSUAA`.
  - A scope the application grants to its own client-credentials tokens through the top-level `authorities` list (a job-scheduler or callback scope, for example) is still reported, because `authorities` is never read; such a scope is used by the application itself rather than assigned to a user, and the finding can be closed by granting it to the calling application explicitly or by accepting it as a known technical scope.
  - Only `scope-references` of role templates count as usage. A scope checked in code (`req.user.is('admin')`, `checkScope` in an approuter or XSSEC handler) without a role template is still reported, because it still cannot be assigned to anyone; the finding then asks for the role template, not for code changes.
  - Scope and reference names that are not identifier-shaped (for example `$XSAPPNAME(application,other-app).read` with parentheses) are dropped by the collector and neither reported nor matched. A `*.mtaext` extension descriptor and `xs-security.json` files under skipped directories (`node_modules`, `gen`, `dist`, dot-directories) are never read, so scopes or templates added only there are not seen.
  - The SAP Help pages were verified through the `SAP-docs/btp-cloud-platform` GitHub mirror: "Application Security Descriptor Configuration Syntax" (`docs/30-development/application-security-descriptor-configuration-syntax-517895a.md`: `scope-references` is "The security scope to apply to the application-related role", `grant-as-authority-to-apps` is used "if you want to grant a scope to other applications for a client credential scenario", and for client credentials "the scopes are granted as authorities") and "Building Roles and Role Collections for Applications" (`docs/50-administration-and-ops/building-roles-and-role-collections-for-applications-eaa6a26.md`: "The user roles are derived from role templates that are defined in the security description", "The application security-descriptor file also contains details of the authorization scopes"). The CAP page was verified through the `cap-js/docs` mirror (`guides/security/cap-users.md`, section "Role Assignment with XSUAA": "For every role name in the CDS model, one scope and one role template are generated with the exact name of the CDS role", `cds compile srv --to xsuaa > xs-security.json`, and the merge sentence quoted above). `help.sap.com` and `cap.cloud.sap` do not resolve from the build environment, so the links are the canonical pages those files publish to. The OWASP link follows the `A02_2025-Security_Misconfiguration` entry in the OWASP/Top10 `2025/mkdocs.yml`.

## APPROUTER_ROUTE_NO_AUTH

**An approuter route hands requests to a backend without a login.** A route in `xs-app.json` with `authenticationType: none` forwards every request to its `destination` or `service` as it arrives: no session, no token, no user. Whatever that backend serves is reachable by anyone who can reach the approuter, and the backend receives no identity it could use for its own checks. When the whole file sets `authenticationMethod: none`, this applies to every route in it.

- **Data:** every `xs-app.json` of the project (`xsApps`): its top-level `authenticationMethod`, and per route the `source` pattern as written, `authenticationType`, which of `destination`/`service`/`localDir` is set, a hint derived from the destination or service name (`ui5-cdn`, `html5-repo`, `api`, `other`; the name itself is not kept) and whether the source matches `logout.logoutPage`. Destination names, `csrfProtection`, `scope`, `cacheControl` and every other property are not used by this rule.
- **Trigger:**
  - a file whose `authenticationMethod` is `none`: one finding per file, the subject is the file path; the routes of such a file are not reported separately, since the file-level setting already covers them;
  - otherwise a route with `authenticationType: none` whose target is a `destination` or a `service`, unless its source (after a leading `^`) starts with `/-/cds/` or `/mt/`, its target hint is `ui5-cdn`, or it is the logout page. One finding per source per project; within a file the first unauthenticated route with that source decides the evidence, across files the API-like occurrence wins, otherwise the first file in path order. The subject is the route source as written.
- **Severity:** from the criticality matrix, both inputs recorded in the evidence. No login is needed in any branch, so the ease of attack is always `easy`.
  - `high` (impact `moderate`, ease of attack `easy`) when the whole file disables authentication, when the destination or service name hints at an API (`srv`, `api`, `backend`), or when the source matches `/odata|\/api|\/rest|\/srv|\/v\d+|graphql/i`: data endpoints are open. (The design review table paired this branch with impact `significant`, which the matrix maps to `critical`; the named severity `high` was kept and the impact lowered, because a CAP or Java backend usually still validates the token itself, so the approuter is one of two layers.)
  - `medium` (impact `minor`, ease of attack `easy`) for every other forwarded route: the target looks like static or HTML5 content, but it is still served without a session and the destination may hide more than that.
- **Evidence:** for a route: `subject` (route source), `target` (`destination` or `service`), `targetHint`, `apiLike` (whether the hint or the source pattern decided `high`), `exemptedRoutes` (count of unauthenticated forwarding routes of the same file that the exemptions silenced), `files` (count of xs-app.json files in which this source forwards without authentication), `impact`, `easeOfAttack`. For a file: `subject` (file path), `authenticationMethod` (`none`), `routes` (count), `impact`, `easeOfAttack`.
- **Location:** the `xs-app.json` file; no line, since the collector keeps route properties only.
- **Remediation:** Remove `authenticationType: none` from the route, or set it to `xsuaa` (or `ias` when the approuter is bound to Identity Authentication), so the approuter forwards only requests with a valid session and passes the user token to the backend. Keep `none` only for routes that serve public static content from a `localDir` or the UI5 CDN, and for the logout page. If the destination must stay reachable without a login, make sure the backend enforces its own authentication and does not trust the approuter to have done it. For a file with `authenticationMethod: none`, set it to `route` (or remove the property; `route` is the default) so that each route decides with its own `authenticationType`.
- **References:** <https://help.sap.com/docs/btp/sap-business-technology-platform/routes>, <https://help.sap.com/docs/btp/sap-business-technology-platform/routing-configuration-file>, <https://owasp.org/Top10/2025/A07_2025-Authentication_Failures/>
- **Limits / what does not trigger:**
  - Only an explicit `authenticationType: none` counts. A route without the property inherits the approuter default (`xsuaa` or `ias`, chosen from the service bindings), and `basic`, `other` and unknown values are not reported. A file without `authenticationMethod` authenticates per route.
  - Routes that serve local files (`localDir`) and routes with no recognisable target are never reported, whatever their authentication type: static content is commonly public, and the rule is about backends.
  - The MTX routes that `cds add approuter` generates (`^/-/cds/.*` for Node.js, `^/mt/.*` for Java) carry `authenticationType: none` by design, because the multitenancy APIs authenticate the SaaS provisioning service themselves; they are exempt. A source that merely contains `/-/cds/` further in (for example `^/app/-/cds/(.*)$`) is not exempt.
  - A route to the UI5 CDN (destination name `ui5`, or containing `sapui5` or `cdn`) and the route that matches `logout.logoutPage` are exempt: SAP documents both with `authenticationType: none`. Whether the UI5 bootstrap itself is safe is the subject of `UI5_BOOTSTRAP_EXTERNAL`.
  - A file with `authenticationMethod: none` produces one finding for the file and none for its routes, so the count of findings is not the count of open endpoints; the `routes` evidence is the number of routes in that file, `localDir` routes included.
  - The collector does not read `httpMethods`, so the rule cannot tell whether an earlier route with the same source shadows a later one. A route with `authenticationType: none` is therefore reported even when an authenticated route with the identical source precedes it: the later route may still answer other HTTP methods, and the `none` is a misconfiguration either way.
  - The same source in several `xs-app.json` files yields one finding (the API-like occurrence, otherwise the first file in path order) with `files` saying how many files carry it; fixing one file moves the finding to the next.
  - The rule does not know what the destination serves. A destination to a backend that enforces its own JWT check is still reported, because the approuter no longer attaches a token and the backend becomes the only line of defence; the `apiLike` evidence and the `high`/`medium` split are heuristics on names and paths, not a probe. Destinations defined only in the subaccount, `xs-app.json` files under skipped directories (`node_modules`, `gen`, `dist`, dot-directories) and `*.mtaext` overrides are never read.
  - `csrfProtection` on an unauthenticated route is irrelevant (CSRF protection applies only to non-public routes) and is not reported here; see `APPROUTER_CSRF_DISABLED` for authenticated routes.
  - The SAP Help pages were verified through the `SAP-docs/btp-cloud-platform` GitHub mirror (`docs/30-development/routes-666eb55.md`: "`none`: No authentication is required for the route", and the default "If you do not define the `authenticationType`, the application router selects the authentication method based on its service bindings"; `docs/30-development/routing-configuration-file-c103fb4.md`: `authenticationMethod` is "The method used to authenticate user requests, for example: “route” or “none” (no authentication)"; `docs/30-development/logout-2296b4d.md`: the logout page route "must be set to `none`"). `help.sap.com` does not resolve from the build environment, so the links are the canonical pages those files publish to. The MTX route shapes come from the design review of `cds add approuter` output. The OWASP link follows the `A07_2025-Authentication_Failures` entry in the OWASP/Top10 `2025/mkdocs.yml`.

## APPROUTER_CSRF_DISABLED

**An authenticated approuter route has CSRF protection switched off.** The application router checks an `x-csrf-token` header on every request other than GET and HEAD (PUT, POST, PATCH, DELETE, ...) to a route that requires a login, and answers 403 without it. A route with `"csrfProtection": false` skips that check, so a page on another site can make the browser of a logged-in user send a write request to the backend with the user's session cookie attached: cross-site request forgery, which OWASP lists under A01 Broken Access Control (CWE-352).

- **Data:** every `xs-app.json` found by the walk (`xsApps`): the top-level `authenticationMethod`, and for each route its `source`, `authenticationType`, `csrfProtection` and which of `destination`, `service` or `localDir` it names. The destination name is not stored, only a hint computed from it. `scope`, `target`, `httpMethods`, `cacheControl`, `identityProvider` and every other route property are never read.
- **Trigger:** a route with an explicit `"csrfProtection": false` that forwards to a `destination`, whose `authenticationType` is not `none`, in a file whose `authenticationMethod` is not `none`. A missing `authenticationType` counts as authenticated: the router then picks `xsuaa` or `ias` from its service bindings. One finding per route source per project (the first file in name order when the same source is disabled in several files); the subject is the route `source` as written.
- **Severity:** from the criticality matrix, both inputs recorded in the evidence.
  - `medium` (impact `moderate`, ease of attack `advanced`), always: the attacker needs a victim who is logged in and visits a page they control, and the damage is limited to what that user may already do; the request goes through with the user's authorization, not beyond it.
- **Evidence:** `subject` (route source), `authenticationType` (`xsuaa`, `ias`, `basic`, `other` or `null` when the route leaves it to the bindings), `authenticationMethod` (`route`, `other` or `null`), `targetHint` (`api`, `ui5-cdn`, `html5-repo` or `other`, computed from the destination name), `routes` (count of routes in the file), `files` (count of xs-app.json files that disable CSRF protection on this source), `impact`, `easeOfAttack`.
- **Location:** the `xs-app.json` file; no line, since the collector keeps route facts only.
- **Remediation:** Remove `"csrfProtection": false` from the route in xs-app.json (the default is `true`), so the application router answers 403 to every request other than GET and HEAD (PUT, POST, PATCH, DELETE, ...) that carries no valid `x-csrf-token` header. Clients obtain the token with a GET or HEAD request that sends `x-csrf-token: fetch`; the SAPUI5 OData models and the CAP Fiori preview do this on their own. If the route only ever serves GET and HEAD, CSRF protection costs nothing, so there is no reason to switch it off. If `cds add app-frontend` generated the route, set the flag back to `true` after generating and let the frontend fetch the token.
- **References:** <https://help.sap.com/docs/btp/sap-business-technology-platform/routes>, <https://help.sap.com/docs/btp/sap-business-technology-platform/application-router-configuration>, <https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html>, <https://owasp.org/Top10/2025/A01_2025-Broken_Access_Control/>
- **Limits / what does not trigger:**
  - A route without `csrfProtection`, or with `csrfProtection: true`, produces nothing: the application router's default is `true` (SAP Help, "Routes": "Toggle whether this route needs CSRF token protection. The default value is “true”.").
  - A public route (`authenticationType: none`) and every route in a file with `authenticationMethod: none` produce nothing, because the router applies CSRF protection only to routes that require a login (SAP Help, "Application Router Configuration", CSRF Protection: "A path is considered public, if it does not require authentication. This is the case for routes with `authenticationType: none` or if authentication is disabled completely via the top level property `authenticationMethod: none`"). Whether such a route should be public at all is the subject of `APPROUTER_ROUTE_NO_AUTH`.
  - Routes to a `service` (for example `html5-apps-repo-rt`) or a `localDir`, and routes naming none of the three targets, are not reported, following the design review table: the flag matters where state-changing requests reach a backend through a destination. A `service` route that proxies writes to a reused service instance is therefore not seen.
  - `cds add app-frontend` generates `"csrfProtection": false` on the OData route (`^/?odata/(.*)$` to destination `srv-api`; `authenticationType: xsuaa` only when the project has xsuaa, otherwise the route leaves it to the bindings) of the `xs-app.json` it writes, which a Vite setup moves to `app/<name>/public/xs-app.json`; the finding is intended there and the remediation applies as it stands. `cds add approuter`, `cds add html5-repo` and `cds add workzone-standard` write the same `srv-api` route with `"csrfProtection": true`, which does not trigger. (Templates `lib/init/template/{app-frontend,approuter,html5-repo,workzone-standard}/files/xs-app.json.hbs` of `@sap/cds-dk` 10.2.0, read from the npm registry tarball.)
  - The rule does not know which HTTP methods the route accepts: a route that lists only `GET` and `HEAD` under `httpMethods` is still reported, since the collector does not read that property; the flag can simply be removed there.
  - When the same route source is disabled in several `xs-app.json` files of one repository, only one finding is produced, located in the first file by name, with `files` counting the others. `xs-app.json` files under skipped directories (`node_modules`, `gen`, `dist`, dot-directories) are never read, and a `*.mtaext` extension descriptor cannot change routes.
  - The SAP Help pages were verified through the `SAP-docs/btp-cloud-platform` GitHub mirror (`docs/30-development/routes-666eb55.md` for the `csrfProtection` default and the `authenticationType` values `ias`, `xsuaa`, `basic`, `none`; `application-router-configuration-c19f165.md` for the CSRF Protection section quoted above, which also states the scope "any HTTP method that is not `GET` or `HEAD`" and the 403 answer; `authenticationmethod-ff58bb0.md` for `route` (default) and `none`). `help.sap.com` and `cheatsheetseries.owasp.org` do not resolve from the build environment, so the links are the canonical pages those files publish to; the cheat sheet was verified through the `OWASP/CheatSheetSeries` mirror (`cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.md`). The OWASP link follows the `A01_2025-Broken_Access_Control` entry in the OWASP/Top10 `2025/mkdocs.yml`, whose page (`2025/docs/en/A01_2025-Broken_Access_Control.md`) lists CWE-352 among its notable CWEs. The `@sap/approuter` README on npm is cut off before its CSRF section and was not used.

## DEPLOY_ARTIFACT_IN_REPO

**A built deployment archive (`.mtar`) lies in the project and no `.gitignore` pattern excludes it.** The Cloud MTA Build Tool writes the archive to `mta_archives/` next to the sources by default, and the archive holds everything the deployer needs: the deployment descriptor, the module and resource binaries and configuration files. For every builder except `maven`, `mbt build` packages the module's folder as it is, so whatever lay there when the build ran (installed dependencies, a `default-env.json` or a service key left next to the sources) is in the archive unless a `build-parameters.ignore` entry excludes it. Without an ignore pattern the next `git add .` commits the archive, and a repository history keeps it even after the file is deleted. A committed archive also invites a deployment from the repository instead of from a pipeline build.

- **Data:** every `*.mtar` outside the skipped directories (`node_modules`, `.git`, `gen`, `dist`, `dist-report`, `target`, `build`, `coverage`, dot-directories), recorded as `archives[]` with the relative file name, its size from `lstat` and whether a `.gitignore` pattern matches it; the archive itself is never opened. `repository` is whether a `.git` entry exists in the project root or in one of its ancestors up to the file-system root (at most 64 levels; `lstat` only; a `.git` file of a worktree counts too), and `gitIgnore.present` whether a root `.gitignore` exists as a regular file. Matching uses the `.gitignore` files of the directories between the repository root and the project root (read for their decision only; never listed, counted or stored), the root `.gitignore` and the `.gitignore` files in the directories along the archive's path (comments, blank lines, `!` negation, leading `/` anchoring, trailing `/`, `*`, `?`, `**`, character classes, patterns without a `/` at any depth, last match wins).
- **Trigger:** an archive with `ignored === false`. One finding per archive file per project; the subject is the relative file name.
- **Severity:** from the criticality matrix, both inputs recorded in the evidence.
  - `medium` (impact `moderate`, ease of attack `advanced`) when `repository` is true: a `.git` entry (directory or worktree file) is present, so the archive is one `git add .` away from the history, or already in it.
  - `low` (impact `minor`, ease of attack `complex`) when `repository` is false: nothing tracks the folder yet, so the archive only lingers on disk until the project is put under version control or packed up and shared, an extra step before anyone else can get at it. (The design review table wrote this cell as `minor` × `advanced`, which the matrix maps to `medium`; `complex` is the pair that yields the intended `low`.)
- **Evidence:** `subject` (archive file), `bytes` (size), `ignored` (always `false`), `repository`, `tracked` (always `'unknown'`: the scan runs no `git` command, so whether the file is already committed is not known), `impact`, `easeOfAttack`.
- **Location:** the archive file; no line.
- **Remediation:** Add `*.mtar` (or the build output folder, usually `mta_archives/`) to the root `.gitignore`. If the archive was already committed, stop tracking it with `git rm --cached <file>` and commit; if it reached a shared remote, treat every credential in its configuration files as exposed and rotate it, since removing the file does not remove it from the history. Build the archive in the pipeline with `mbt build` and deploy from there instead of keeping it next to the sources.
- **References:** <https://git-scm.com/docs/gitignore>, <https://sap.github.io/cloud-mta-build-tool/usage/>, <https://help.sap.com/docs/btp/sap-business-technology-platform/multitarget-applications-in-the-cloud-foundry-environment>, <https://owasp.org/Top10/2025/A03_2025-Software_Supply_Chain_Failures/>
- **Limits / what does not trigger:**
  - An archive that a `.gitignore` pattern matches produces nothing, whether or not the folder is a repository. The rule checks the ignore configuration, not the index: an archive that was committed before the pattern was added is still in the history, yet it counts as ignored and produces no finding, hence `tracked: 'unknown'` on the findings that are emitted. Running `git ls-files '*.mtar'` answers that question.
  - Only `.gitignore` files are read: `.git/info/exclude`, the global `core.excludesFile` and the ignore rules of other version control systems are not, so an archive excluded only there is reported. Conversely, the matcher treats a file inside an ignored directory as ignored even when a deeper pattern re-includes it, which matches git ("It is not possible to re-include a file if a parent directory of that file is excluded").
  - A root `.gitignore` that exists but does not cover the archive still triggers; the `gitIgnore.present` flag changes nothing. The pattern must come from the project itself: the repository that ships `btp-lens` ignores `*.mtar`, but that does not help a scanned project.
  - Archives under skipped directories (for example `dist/` or `target/`) are never seen, and the walk stops after 20 000 entries or 200 archives. Other packaged artifacts (`.zip`, `.jar`, `.war`, `.tgz`) are out of scope: the rule is about the MTA archive, the artifact `mbt build` writes into the project by default.
  - `repository` is the presence of a `.git` entry in the project root or one of its ancestors (a CAP project is often a folder inside a larger repository), and the `.gitignore` files between that repository root and the project root are honoured, so an archive that a parent `.gitignore` excludes, or a project folder that one excludes altogether, produces nothing. A project whose `.git` lives elsewhere (`--git-dir`, `GIT_DIR`) is reported as `repository: false` and therefore `low`; a `.git` directory left by a template clone, or one more than 64 levels up, counts as present or absent accordingly.
  - The `gitignore(5)` manual was verified through the `git/git` GitHub mirror (`Documentation/gitignore.adoc`: "Files already tracked by Git are not affected; see the NOTES below for details", "To stop tracking a file that is currently tracked, use `git rm --cached` to remove the file from the index"); the link is the canonical page it publishes to. The Cloud MTA Build Tool usage page was verified through the `SAP/cloud-mta-build-tool` mirror (`docs/docs/usage.md`: "If this parameter is not provided, the `MTAR` file is saved in the `mta_archives` subfolder of the current folder", default name `<mta_application_ID>_<mta_application_version>.mtar`; `docs/docs/configuration.md`: the default `build-result` is "`<module's folder>`" for every builder but `maven` and `fetcher`, and `ignore` lists "Files and/or subfolders to exclude from the package"); `sap.github.io` does not resolve from the build environment, so the link is the canonical published page. The SAP Help page was verified through the `SAP-docs/btp-cloud-platform` mirror (`docs/30-development/multitarget-applications-in-the-cloud-foundry-environment-d04fc0e.md`, which defines the archive as "Archive containing a deployment descriptor, the module and resource binaries, and configuration files"); `help.sap.com` does not resolve either, so the link is the canonical page that file publishes to. The OWASP link follows the `A03_2025-Software_Supply_Chain_Failures` entry in the OWASP/Top10 `2025/mkdocs.yml`, whose page recommends to "promote artifacts rather than rebuilding for each environment, ensure builds are immutable".

## SEED_DATA_SENSITIVE

**A seed CSV file carries payment card numbers, IBANs or secrets.** Files under `db/data`, `db/csv` or `test/data` are committed with the project and loaded into the database by `cds deploy`, so a column of real card numbers, bank accounts or credentials ends up in every clone of the repository and in every system the project is deployed to, in clear text. Card numbers and IBANs are personal and financial data that must not be stored unprotected; a secret in seed data is a credential that every developer, pipeline and database copy can read.

- **Data:** every seed CSV the collector read (`seedData`): `*.csv` files in a directory named `data` or `csv` reached by the walk, plus `test/data`. For each file: the data row count checked (first 200 rows), whether the header was rejected, and for each column whose name matches a card, IBAN or secret pattern, the column's 1-based position in the header (never its name: a header-less file whose first row is identifier-shaped would otherwise turn a cell value into a "name"), the kind and the number of rows whose value passes the matching check (card: 13–19 digits after removing spaces and dashes, Luhn-valid; IBAN: country code, check digits and 11–30 alphanumerics with mod-97 remainder 1; secret: any value that is not empty or whitespace only). No header name other than the sensitive columns and never a cell value is kept.
- **Trigger:** a sensitive column with `rowsMatching > 0`. One finding per (file, column position) per project; the subject is `<file>#<columnIndex>` (for example `db/data/acme.incidents-Customers.csv#6`), because the same position may be sensitive in several seed files. When a snapshot lists a file or a position twice, the entry with the larger match count is kept (then the larger row count, then the kind in `card`, `iban`, `secret` order), so the result does not depend on the order of the entries.
- **Severity:** from the criticality matrix, both inputs recorded in the evidence.
  - `high` (impact `significant`, ease of attack `advanced`), always: the values are financial data or credentials in clear text, spread to every clone and database, but reading them needs access to the repository, a build artifact or a deployed database rather than an anonymous request.
- **Evidence:** `subject` (`<file>#<columnIndex>`), `columnIndex` (1-based position of the column in the header), `kind` (`card`, `iban` or `secret`), `rowsChecked` (data rows examined, at most 200), `rowsMatching` (rows whose value passed the check), `impact`, `easeOfAttack`.
- **Location:** the CSV file; no line, since the collector keeps counts only and the values are spread over the data rows.
- **Remediation:** Remove the real values from the CSV file: replace card numbers and IBANs with clearly synthetic, masked values that fail the format checks (for example `****-****-****-1111`), leave secret columns empty, or drop the column from the seed file altogether. Secrets belong in a service binding or a credential store, never in seed data. Keep `db/data` for configuration data and code lists that must reach production; test data belongs in `test/data`, which CAP loads in development only. If the values are real, treat them as exposed: rotate the secrets and remove the file from the repository history as well, since deleting it in a new commit leaves it in every clone.
- **References:** <https://cap.cloud.sap/docs/guides/databases/initial-data>, <https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html>, <https://owasp.org/Top10/2025/A04_2025-Cryptographic_Failures/>
- **Limits / what does not trigger:**
  - Both the column name and the values must match. A column called `password` whose cells are all empty, or a `creditCardNo` column holding masked values such as `****1111`, has `rowsMatching: 0` and produces no finding. Conversely the rule cannot tell real values from well-formed test values: the public test card numbers (`4111 1111 1111 1111`, `5500 0000 0000 0004`) are Luhn-valid and are reported on purpose, because the seed file still trains everyone to put card numbers there and the check would otherwise be trivial to satisfy with a real number.
  - The `secret` kind accepts any value that is not blank, so a placeholder like `changeme` in a `password` column is reported; the remediation is the same (keep the column empty in seed data). Blank cells (empty, or spaces only) do not count.
  - Only column names are matched, not contents of other columns: a card number in a `notes` or `description` column, or in a file whose header is not identifier-shaped (`headerRejected`, including header-less exports such as `Poison,Person,…`), is not seen. Column names the patterns do not cover (`accountNumber`, `cc`, `pin`) are not seen either; names like `idCard`, `giftCard`, `scoreCard` are deliberately excluded from the card pattern.
  - Only the first 200 data rows of each file are checked, so `rowsMatching` is a lower bound; files over 2 MiB are recorded as unreadable and not checked; CSV files outside a `data`/`csv` directory or `test/data`, under skipped directories (`node_modules`, `gen`, `dist`, dot-directories) or beyond the walk limits are never read.
  - The rule does not know whether the file is deployed: `test/data` is loaded in development only, and a file may be excluded by build configuration. It is reported anyway, since the values are in the repository either way; the file path in the location shows which case applies.
  - The CAP page was verified through the `cap-js/docs` GitHub mirror (`guides/databases/initial-data.md`, "Adding Initial Data": the default folders are `db/data` and `test/data`, `test/data` is loaded "in development only", and initial data is "meant for production (configuration, code lists)"); the OWASP cheat sheet through the `OWASP/CheatSheetSeries` mirror (`cheatsheets/Secrets_Management_Cheat_Sheet.md`, which describes hardcoded plaintext secrets in source code as the problem the sheet addresses). `cap.cloud.sap` and `cheatsheetseries.owasp.org` do not resolve from the build environment, so the links are the canonical pages those files publish to. The OWASP Top 10 link follows the `A04_2025-Cryptographic_Failures` nav entry and `site_url` in the OWASP/Top10 `2025/mkdocs.yml`.

## UI5_BOOTSTRAP_EXTERNAL

**An HTML page bootstraps SAPUI5 from an external host without an `integrity` attribute.** The bootstrap script (`sap-ui-core.js`) runs with the full authority of the page: it initializes the runtime and then fetches every library, control and resource the app needs from the same origin at run time. When that origin is a public CDN the application executes whatever the CDN serves, and with the unversioned URL form (`https://ui5.sap.com/resources/sap-ui-core.js`) that code changes whenever SAP publishes a new maintenance version, without a deploy and without a trace in the project. A compromised or spoofed CDN response, a DNS or proxy manipulation on the user's network, or simply an incompatible new version then reaches every user session. An `integrity` attribute lets the browser refuse a loader that does not match the expected hash; it is a partial defence (it covers only the one script, not what the loader fetches afterwards), but together with a pinned version it is the most the page itself can do when the CDN stays.

- **Data:** every `*.html` file outside the skipped directories, recorded in `html[]` when it contains a `<script>` with `id="sap-ui-bootstrap"` or a `src` ending in `sap-ui-core.js`: the relative file name, the line of the script tag, the `src` reduced to origin and path, at most 200 characters (userinfo, query and fragment are dropped; a protocol-relative `//host/path` is recorded as `https://host/path`; `[non-http]` for other schemes), `external` (absolute `http(s)` or protocol-relative URL), `integrity` (attribute present; its value is never stored), `versionForm` (`specific` for a `/1.120.3/` segment, `evergreen` for `/1.120/`, `latest` for an external URL without either, `none` for a relative src) and `testPage` (a `test/` path segment, or a file name like `flpSandbox.html` or `*.qunit.html`).
- **Trigger:** a bootstrap with `external === true` and `integrity === false`. One finding per HTML file per project; the subject is the relative file name. When a file holds several such bootstraps the one with the unpinned `latest` form on a non-test page wins, otherwise the first in the file (on one line, the lower `src`), so the pick does not depend on the order the collector emitted them.
- **Severity:** from the criticality matrix, both inputs recorded in the evidence.
  - `medium` (impact `moderate`, ease of attack `advanced`) when `versionForm` is `latest` and the page is not a test page: the code the users run changes with every CDN release, and nobody can say which version ran when.
  - `low` (impact `minor`, ease of attack `complex`) otherwise: a `specific` or `evergreen` version still trusts the host, but a swap would have to target a fixed artifact; a test page (`flpSandbox.html`, QUnit pages, anything under `test/`) is a development aid and not what end users open. (The design review table wrote this cell as `minor` × `advanced`, which the matrix maps to `medium`; `complex` is the pair that yields the intended `low`.)
- **Evidence:** `subject` (HTML file), `host` (the host name of the `src`, or `null` when the `src` is not an absolute URL with a DNS-shaped host; never the path, port, userinfo, query or fragment), `versionForm`, `testPage`, `impact`, `easeOfAttack`.
- **Location:** the HTML file and the line of the bootstrap `<script>` tag.
- **Remediation:** Serve SAPUI5 through the approuter instead of a public CDN: route `resources/` to the `ui5` destination or to the HTML5 Application Repository, so the version is controlled by the landscape and does not change behind a deployed app. Where the CDN must stay, pin a specific version (`https://ui5.sap.com/1.120.3/resources/sap-ui-core.js`) rather than the evergreen or unversioned form, and add `integrity="sha384-…"` with `crossorigin="anonymous"` to the bootstrap script, knowing that they protect only the loader: the libraries it fetches at run time are still trusted blindly. Keep the pinned version inside maintenance, since the CDN removes versions one year after their end of maintenance.
- **References:** <https://ui5.sap.com/#/topic/2d3eb2f322ea4a82983c1c62a33ec4ae> (Variant for Bootstrapping from Content Delivery Network), <https://me.sap.com/notes/3001696> (SAP Note 3001696), <https://owasp.org/Top10/2025/A08_2025-Software_or_Data_Integrity_Failures/>
- **Limits / what does not trigger:**
  - A bootstrap served relative to the page (`resources/sap-ui-core.js`, `/resources/sap-ui-core.js`), which is what the approuter `ui5` destination and the HTML5 Application Repository produce, is never reported, whatever version segment its path carries; neither is a `src` with a scheme other than `http(s)` (recorded as `[non-http]`).
  - An external bootstrap with an `integrity` attribute is not reported, even with the `latest` form and even though SRI covers only the loader: the rule checks the page's own defence, not the run-time loading of libraries. The attribute's value is never read, so a wrong or stale hash (which would make the browser block the script) is not detected either; the page would fail visibly.
  - The scan does not know the host an app will be deployed to, so an absolute URL pointing at the app's own origin, at `localhost` or at a company-internal server is reported like a public CDN: `external` means "not relative to the page". Serving the bootstrap relative to the page removes the finding and is what the approuter produces anyway.
  - `host` is recorded as an identifier of the CDN only when it has the shape of a DNS name (no trailing dot; an internationalized name appears in its punycode form) or a dotted IPv4 address; a bracketed IPv6 host, an empty host or an unparsable `src` is recorded as `null`, and the finding still fires because the collector flagged the bootstrap as external.
  - Only `<script>` tags that the collector recognises as a bootstrap count (`id="sap-ui-bootstrap"` or a `src` ending in `sap-ui-core.js`). Bootstraps assembled at run time (`sap-ui-core-nojQuery.js`, loaders injected by JavaScript, `ui5loader.js`, frameworks that write the tag) and pages generated at build time (`gen/`, `dist/`) are not seen; every `<script>` tag of a page is examined, whatever its position, and at most 200 bootstraps per file and 200 per project are recorded.
  - The rule does not check whether the pinned version is still in maintenance or still on the CDN; `UI5_OUT_OF_MAINTENANCE` covers the version served by a deployed app. A `specific` version that the CDN has removed (SAP Note 3001696: one year after end of maintenance) fails at run time, which is an availability problem rather than an integrity one.
  - The SAPUI5 CDN topic was verified through the `SAP-docs/sapui5` GitHub mirror (`docs/04_Essentials/variant-for-bootstrapping-from-content-delivery-network-2d3eb2f.md`: "The default version of our libraries has the generic URL `https://ui5.sap.com/resources/sap-ui-core.js`", "The specific version allows you to select a particular fixed version for bootstrapping", "The evergreen version allows you to automatically select the latest available patch level", "SAP removes SAPUI5 versions from the SAPUI5 CDN one year after their end of maintenance. For more information, see SAP Note 3001696"; the word "integrity" does not appear in the topic), and the bootstrap description through `docs/04_Essentials/bootstrapping-loading-and-initializing-a04b0d1.md` ("Required files are loaded dynamically using XMLHttpRequest (XHR)", "You can access the libraries externally from a CDN, which can be either an SAP-hosted CDN or a custom-hosted CDN"). `ui5.sap.com` does not resolve from the build environment, so the link is the canonical topic URL that file publishes to. SAP Note 3001696 is cited by that topic; `me.sap.com` does not resolve either and requires an SAP account, so the link is the canonical note URL and its content was not read. The OWASP link follows the `A08_2025-Software_or_Data_Integrity_Failures` entry in the OWASP/Top10 `2025/mkdocs.yml`, whose page names applications that rely "upon plugins, libraries, or modules from untrusted sources, repositories, and content delivery networks (CDNs)".
